# 设置与运行状态融合驱动方案

## 方案定位

本方案保持 settings 与 runtime 的所有权分离，同时增加进程内 pending 作为一次性离线反馈桥梁：
settings 保存目标，runtime 保存并驱动实际状态；只有后端 HTTP 不可达时才记录 pending。
后端可达时不做本地退化：读到实际值就由实际值驱动；485 数据陈旧时保持最后一次有效值并另行提示，
不得使用 pending 冒充设备实际状态。后端不可达且本轮没有实际值时，pending 才补入 runtime，保证
纯 UI 或离线环境仍有可见反馈。

本方案适合以下场景：

- 正式环境要求 UI 以实际状态为准，同时纯 UI 或离线环境也要具备可见交互反馈；
- 设置提交和运行读取都能归一到各自的单一写入链路；
- 可以明确区分成功、明确拒绝和暂时不可用；
- 可以接受 pending 只存在于当前进程、不会跨重启保存。

本方案不适合以下场景：

- 产品要求离线操作也具备真实外部回执语义；
- 无法可靠区分明确拒绝与暂时不可用；
- 多个应用或进程要共享同一个 pending；
- 状态变化频率很高，不能使用统一快照刷新链路。

## 优点与缺点

### 优点

- 外部数据正常时，UI 始终服从实际 runtime；
- 外部数据暂时不可用时，纯 UI 联调仍能通过统一刷新链路立即看到操作结果；
- pending 不直接写 runtime，避免设置链路成为第二个 runtime 写入方；
- 主动刷新与周期刷新共用同一非重入入口，冲突边界清楚；
- 后端写成功后只回读本次连续的 N 个数据单元，无需等完整轮询才确认状态；
- 前端写后补读与周期读共用一个快照入口，不会并发重入；
- 后续可把 pending 从单字段扩展为字段补丁或组合补丁，而不改变数据所有权。

### 缺点

- 比单一数据源多出 pending 的创建、保留、消费和清除规则；
- pending 只是一次即时反馈值，不能证明外部对象已经执行成功；
- 写后补读使用末次写入防抖，连续操作会把这一次额外补读向后顺延；
- 如果成功、拒绝和暂时不可用分类错误，可能产生不应出现的降级显示；
- 多字段组合需要定义整体成功、部分失败和实际值覆盖策略。

## 1. settings 与 runtime 的数据所有权

| 数据 | 正常写入方 | 负责内容 | UI 使用方式 |
|---|---|---|---|
| settings | 设置或控制提交链路 | 用户设置目标 | 驱动设置项，不直接驱动运行状态 UI |
| runtime | 统一运行数据刷新链路 | 实际运行状态和运行快照 | 驱动运行状态 UI |
| pending | 进程内降级反馈链路 | 后端 HTTP 不可达时，用户已确认保存的一次性意向值 | 本轮仍确认后端不可达时，补入 runtime 一次 |

必须遵守：

- settings 与 runtime 分开保存、分开校验、分开恢复；
- 设置提交函数不得直接写 runtime；
- 运行刷新函数不得覆盖 settings；
- pending 只表示用户意向，不表示外部对象已执行，也不是第三种实际状态数据源；
- pending 只存在于内存，不作为第三份持久化数据；
- pending 只在后端 HTTP 不可达时补充对应字段；后端可达、485 数据陈旧或读到实际值时均不得使用；
- 页面只提交目标并消费刷新结果，不直接拥有 runtime 写入权。

## 2. 何时读取、何时写入

应用启动：

```text
读取 settings
  -> 完整校验
  -> 读取 runtime
  -> 完整校验
  -> settings 初始化设置目标
  -> runtime 初始化运行状态 UI
```

用户提交控制：

```text
锁定当前提交入口
  -> 形成控制目标
  -> 执行控制
       ├─ 明确拒绝：不保存目标，不记录新 pending，并清除同字段旧 pending
       ├─ 成功：进入 settings 提交流程，不记录 pending
       └─ 后端 HTTP 不可达：进入 settings 提交流程
  -> 原子写入并完整读回 settings
  -> settings 读回成功且后端不可达：记录 pending，尝试触发统一 runtime 刷新
  -> settings 读回失败：不保留本次 pending
  -> 解除提交锁定
```

后端 HTTP 返回“成功”的准确语义是控制命令已通过校验并成功进入 Modbus
调度队列，不表示设备已经执行，也不允许前端据此把目标值当成实际状态。

### 2.1 后端外部设备写后确认读

```text
HTTP 控制请求
  -> 策略校验并形成本次连续 N 个数据单元的写入内容
  -> 命令进入通信写队列，HTTP 立即返回 accepted
  -> 调度器按“写优先、一拍一任务”执行
  -> 写帧完整成功
  -> 把同一起始位置、同一 N 个数据单元的确认读放入读队列
  -> 确认读完整成功
  -> 状态中心在同一把数据锁内整组替换原始数据
  -> 从完整数据镜像重新解析业务字段
  -> 一次发布新快照
```

必须遵守：

- 写失败时不启动确认读；
- 确认读失败、数量不等或越界时，不发布半组数据；
- 写入和确认读都仍由同一通信调度器串行执行，不绕过通信脉搏；
- 正常周期读和写后确认读可以共存，写队列仍拥有优先级；
- 本次写了 N 个连续数据单元，就必须整组回读同样的 N 个数据单元。
- 写事务成功时已经重置通信新鲜度；确认读成功时再次重置。缓存发布与
  `dataFresh` 计时是两个职责，不能要求整组业务快照发布后才算通信成功。

对于存在互斥或联动的组合字段，后端保留一份受锁保护的“最新已接受组合意向”，
用于连续点击时组装下一个完整组写，避免尚未读回的前一次操作被旧快照覆盖。
这份意向不是实际运行状态：完整组确认读成功后与实际值同步；写失败、
确认读失败或只读到联动组的一部分时立即失效，不允许继续使用不完整基准。

互斥规则只用于后端组装控制写，不用于修饰设备读回。周期读或确认读即使取得
不符合互斥关系的组合，状态中心也必须把这次完整读回作为一次“原子事务更新”，
按设备实际值同时发布原始镜像和业务字段，前端照常显示；下一次控制发生时，
后端写策略再把该事实基准整理成符合规则的原子组写事务。

### 2.2 前端周期读与写后补读

前端保留可配置的统一运行快照周期读取（当前落地值约 2 秒）。后端 HTTP 接受写入后，
另外启动一个可调的一次性计时器（当前落地值 350ms），并采用“末次写入后再等待”的尾沿防抖：

```text
0ms   发生第一次已接受写入 -> 原定 350ms 补读
100ms 发生第二次已接受写入 -> 取消前一计时，重新计时
450ms 执行一次统一运行快照补读
```

- 350ms 是前端常量，后续可根据实机通信节奏单点微调；
- 一次性计时器不在函数内睡眠，不阻塞 UI 线程；
- 若触发时周期读正在执行，只记一个待补读标志；当前请求结束后立即补读一次；
- 重叠的多个补读请求只合并成一次，不积累无限队列；
- 持续快于防抖间隔的写入可以持续顺延这一次额外补读，但独立的周期读仍正常运行，所以不会造成整体读取饥饿；
- 后端 HTTP 不可达时不启动 350ms Modbus 补读等待，直接走本地 pending 降级刷新。

### 2.3 dataFresh 的语义

`dataFresh` 只使用单调时钟计算，不依赖可能不准的系统时间。任意一次真实的
外部设备读事务或写事务成功，都会立即把新鲜度计时清零；一次完整周期采集中的
某个合法分段读成功也算成功通信。串口仅打开成功、命令仅进入队列、解析线程仅发布
已有缓存，都不能清零。自最后一次成功通信起未满 30 秒时为 `true`，达到 30 秒即
为 `false`。后端仍保留最后一份有效值，前端只显示“设备数据陈旧”提示，不把实际值
清零，也不用 pending 覆盖它。

### 2.4 本机能力的确认策略

本机能力可以与外部设备控制复用统一的提交入口、失败分类、非重入保护和快照发布机制，
但不能强制所有能力都采用写后回读。每项能力应根据平台接口明确选择一种确认策略：

1. **可靠回读**：写入成功后等待该能力独立配置的确认延时，再读取实际值并发布快照；
   UI 以读回值为准。机制可以与外部设备的写后确认读相同，但延时不能共用一个固定值。
2. **返回值确认**：平台写接口直接返回最终生效值时，以该返回值作为确认结果并发布，
   不再追加一次回读。
3. **无回读接口**：UI 可以先显示用户目标，再执行写入；写入成功后保持，明确失败时回滚。
   此时显示的是已接受设置，不得描述为经过设备实际状态确认。

平台调用结果按接口自身能够提供的最小契约判定：有明确成功、失败结果时直接采用；接口为
`void` 或没有返回状态时，只要调用正常完成且没有可检测的异常或系统错误，就按写入成功处理，
并把请求值作为最后一次成功目标发布到 runtime；平台返回实际生效值时，实际值优先于请求值。
调用失败或存在明确错误时保留上一份确认值，前端回退到该值，不主动向设备执行物理回滚。

“本地数值调整器”是第一类可靠回读能力的一种通用实例：前端分别保存设置目标和后端
实际值；后端 HTTP 不可达时显示本地设置，后端可达时由最后一次确认的实际值接管，不能
让尚未确认的设置目标冒充实际值。提交后按该能力独立配置的确认延时补读一次；回读成功
采用实际值，明确失败或回读失败恢复上一次确认值。该模型不绑定具体设备、数值范围或
平台接口。

确认策略属于单项能力配置，不改变 settings、runtime 与 pending 的总体所有权；是否回读、
确认延时和最终状态来源必须集中定义，不能散落在页面控件中。

### 2.5 过程型本机操作

扫描、连接、断开一类过程型操作不能塞进页面控件，也不能与外部总线轮询共用执行线程。前后端各自
保留一个页面无关的管理器：后端管理器顺序执行平台命令并持续发布过程状态，前端管理器只提交命令、
消费统一运行快照和协调本地凭据。页面离开只销毁页面显示，不取消已经接受的后台操作。

过程状态至少应区分：

```text
idle
scanning
connecting
connected
disconnecting
failed
disabled
unavailable
```

前端仍只读取一份聚合 runtime，过程型操作的可用性、开关、连接状态、目标标识、实际标识、地址、
扫描结果、pending 和 error 都是其中一个分区，不为每个字段再发独立 HTTP 请求。网络详情页的
`GET /api/local-device/wifi/scan` 是一个例外的按需读取入口：真实扫描仍由后端串行执行，前端不直接
操作模组；扫描结果位于统一响应包装的 `data.current` 和 `data.networks`。写命令返回 `accepted` 只表示
进入后端队列；只有前端主动连接事务先观察到同一 SSID 的
`connecting`，再由后续聚合快照确认实际连接成功，才能把本次凭据写入 settings。

过程状态在前端采用“单次计算只使用一份快照”的轻量事务边界。一次聚合读取把同一响应中的过程字段
归一化为一份完整状态组；同一次页面构建、按钮可用性判断或操作决策先取得该状态组，后续不再分别从
本地样板和后端 runtime 拼接字段。该边界不要求跨 HTTP 往返强一致，也不改变原有刷新节奏：界面可以
短暂显示上一份完整状态，下一次正常聚合轮询再按最新状态纠正；不得因此增加同步等待、额外重试或新的
高频轮询。页面周期、详情页懒加载周期和过程型操作优先级继续由原有策略控制。

凭据规则：

- 同一标识只保留一份最近确认成功的凭据，不区分它最初来自离线样板还是真实设备；
- 输入框不预填测试密码或历史密码，使用已保存凭据的直接连接流程也不能把密码显示出来；
- 连接失败不覆盖旧凭据，普通断开不等于忘记，未实现“忘记”操作时不得暗中删除；
- 模组或命令行建立的连接只展示，不保存凭据；密码弹窗期间若同一 SSID 已连接，不重复发连接命令，
  也不保存本次输入；
- 前端主动连接必须完整观察到同一 SSID 的 `connecting -> connected` 才能保存凭据；过程缺失、目标
  不一致、失败或超时都不得保存；
- 开放网络的空凭据只在真实后端按实际扫描结果处理，不能与离线样板规则混用；
- 后端不持久化、不回传、不记录凭据，只在一次连接命令的执行期临时使用；
- 后端 HTTP 不可达时可以启用集中配置的离线样板规则，但后端一旦可达，必须完全服从真实过程状态。

开关不是一次临时按钮状态，而是需要持久化的连接策略。统一同步规则如下：

- App 启动时按已保存开关执行一次同步，不使用上次 runtime 猜测当前连接；
- 最近成功凭据最多保存 10 个；扫描列表与凭据表独立，按 SSID 去重、信号强度排序并最多展示 20 个，扫描不得新增、覆盖或删除凭据；
- 开关为关闭时统一执行一次关闭：后端可达就提交真实 `enabled=false`，后端不可达就清除本地 JSON 连接态；
- 上述关闭语义不区分真实设备与离线测试模式，两者都不允许保留“已连接”展示；
- 后端从可达变为不可达时只断开一次，不在每个轮询周期重复清空；之后用户主动建立的离线测试连接可保持到主动断开或后端恢复；
- 后端恢复且已保存开关为开启时，只同步一次开启命令，不根据保存凭据主动连接；模组自身负责重连；
- 启动同步和后端恢复同步都是边沿事件，不能在每两秒运行快照轮询中重复发送命令。

“关闭 Wi-Fi”与“断开当前连接”必须分开：关闭会使 `enabled=false` 并禁止扫描、连接；
普通断开只清除当前 SSID/IP，保持开关、扫描结果和凭据不变。普通断开后仍可进入网络详情页并主动
扫描或连接；前端不得因为后续快照显示未连接、重新打开开关或后端恢复而按保存表补发连接。

网络详情页采用懒加载：进入时立即 GET 扫描一次，停留期间每 10 秒再尝试一次，离开立即停止页面
定时器。单次扫描允许后端阻塞最多 12 秒，前端使用 15 秒专用超时；连接、断开或上一轮扫描尚未结束
时跳过本次扫描，不排队、不并发，并在操作结束后重新安排下一周期，避免占满后端 HTTP 工作线程。
后端不可达时不发真实扫描，沿用最后一次有效扫描列表；从未取得列表时显示为空。
系统网络守护进程可能在 App 发命令前自行恢复历史连接，前端对此不猜测来源，只消费板端实际状态；
已经连接时不得为了执行 App 自己的连接策略而重复下发连接命令。

用户在 `scanning/connecting/disconnecting` 期间离开页面时，管理器继续运行；重新进入页面直接用最新
runtime 恢复展示。产品若允许新命令覆盖旧过程，覆盖和排队规则必须由管理器统一定义，不能依赖页面
是否仍在前台。

单个连接事务的总期限为 20 秒，平台连接命令和后续状态确认共用这 20 秒，不能各自再等待 20 秒。
前端同时使用单调计时作兜底，保证异常快照不会让 `connecting` 永久存在。连接失败或超时后清除本次
pending 并提示用户重新输入，不根据保存表恢复、补发或尝试其它网络。

页面返回只结束当前页面的等待显示和扫描定时器，不向后端发送取消连接。平台连接若随后成功，全局
运行快照仍正常接收结果；只有完整满足主动事务确认条件时才保存凭据。用户明确选择另一个 SSID 才
构成新的连接意图。
候选网络扫描与连接事务分别建模，扫描过程不能占住手动选网入口；底层平台工具的串行访问和抢占由
后端管理器统一完成。

统一 runtime 刷新：

```text
刷新任务触发
  -> 上一轮未结束：跳过本次，pending 保留
  -> 复制并清除本轮开始前已经存在的 pending
  -> 顺序执行运行数据读取任务
  -> 汇总本轮读取成功的实际值
  -> 后端可达：保留实际值或最后一次有效值，忽略 pending
  -> 后端不可达：使用 pending 补充对应字段一次
  -> 合并形成完整 runtime 候选值
  -> 原子写入并完整读回 runtime
  -> 校验成功后替换内存 runtime
  -> runtime 驱动 UI 更新
```

- 主动触发刷新与周期刷新使用同一个非重入入口；周期触发遇忙直接跳过，写后触发遇忙则合并一次补读；
- settings 不参加 runtime 的周期刷新；
- pending 只在统一 runtime 刷新链路中使用，设置提交函数不能直接用它刷新运行状态 UI；
- pending 在一次刷新入口被消费；本轮读到的实际值始终优先。

## 3. 原子落盘和读回校验

settings 与 runtime 的每次写入都发布完整文件：

```text
生成完整候选数据
  -> 校验结构、类型、范围和组合约束
  -> 在目标文件同目录写入临时文件
  -> 完成写入并关闭临时文件
  -> 原子替换目标文件
  -> 完整读回目标文件
  -> 再次执行完整校验
```

- settings 读回成功后，只替换内存中的 settings 分区；
- runtime 读回成功后，只替换内存中的 runtime 分区并刷新运行状态 UI；
- pending 只参与 runtime 候选值生成，不单独落盘；
- 多个读取任务只返回本轮内存结果，由统一链路一次发布完整 runtime；
- 不允许设置提交链路和运行刷新链路同时修改 runtime；
- 读取方只能接受旧的完整文件或新的完整文件。

## 4. 失败、冲突和恢复规则

- 明确拒绝：settings 不变，runtime 不因本次控制而改变，不产生新 pending 并清除同字段旧 pending；UI 结束处理中状态后继续显示 runtime；
- settings 写入、原子替换或读回失败：保留上一份有效 settings，不允许本次 pending 继续生效；
- 本轮开始前存在 pending：后端不可达时才补入该字段一次；后端可达时直接忽略；
- 下一轮没有新的 pending：继续完全服从本轮可取得的实际 runtime；
- runtime 写入、原子替换或读回失败：保留上一份有效 runtime 和原 UI 状态；
- 上一次统一刷新未结束时，新的周期触发直接跳过；写后触发则只合并一次，当前刷新结束后立即执行；
- 单个读取任务失败不阻断同一轮其他独立任务；
- 启动时某一份文件不存在或无效：只恢复对应文件，另一份有效文件继续使用；
- 同一进程内，settings 与 runtime 各自只有一个正常写入链路，不增加文件锁；
- 多进程或多个应用需要写同一份数据时，必须改由单一协调者负责写入；
- pending 只用于后端 HTTP 不可达时的单次可见反馈，不能作为外部执行成功的证明。

## 脱敏场景示例

以下示例来自某中控屏设备控制项目的通用数据链路，已去除项目名称、设备名称、字段名称、接口和路径，
只保留可以复用的机制与当前已确定的时序。

### 场景一：无外部数据源，应用启动

```text
应用启动
  -> 分别读取并校验 settings 与 runtime
  -> settings 初始化设置目标
  -> runtime 初始化运行状态 UI
  -> pending 为空
```

首屏不等待外部连接。外部读取失败时继续保留最后一份有效 runtime，不因网络失败重建有效快照。

### 场景二：外部暂时不可用，纯 UI 操作

```text
用户提交目标值
  -> 后端 HTTP 不可达
  -> 原子写入并严格读回 settings
  -> 读回成功后记录 pending
  -> 主动尝试统一 runtime 刷新
       ├─ 当前空闲：刷新链路消费 pending，发布新 runtime，UI 变化
       └─ 正在刷新：本次触发跳过，pending 留到下一次正常刷新
```

可见变化仍来自 runtime，而不是设置函数直接改 UI。pending 不跨重启，也不代表外部执行成功。
当前空闲时，这次主动刷新紧跟在 settings 保存之后执行，不需要等待下一个周期。

### 场景三：外部可用并返回实际状态

```text
用户提交目标值
  -> 外部接受目标
  -> settings 写入并读回成功
  -> 不记录 pending
  -> 末次写入 350ms 后尝试统一补读
  -> 后端写后确认读或正常周期读已发布实际状态
  -> 前端统一快照读到实际状态
  -> runtime 发布后 UI 直接显示实际值
```

若外部实际值与目标值相反，本轮 UI 就必须显示实际值。后端可达但 485 数据陈旧时同样不使用
pending，继续保留最后一次有效设备值，并由独立的陈旧状态提示负责告知用户。

### 场景四：外部明确拒绝

```text
用户提交目标值
  -> 外部明确拒绝
  -> settings 不变
  -> 不产生新 pending，并清除同字段旧 pending
  -> runtime 不因本次控制而改变
  -> UI 结束处理中状态，继续显示 runtime
```

明确拒绝不能退化为“暂时不可用”，否则 pending 会把失败操作伪装成可见成功。

### 场景五：外部中断后恢复

```text
外部中断期间
  -> 刷新读取失败
  -> 有 pending 时允许生成一次降级 runtime

外部恢复后
  -> 下一次实际读取成功
  -> 没有新的 pending 时，实际值覆盖上一轮即时反馈值
  -> UI 回到实际状态
```

因此融合方案解决的是“后端进程不存在时的前端退化 + 后端恢复后实际值重新接管”，不是把一次目标
永久当成实际状态，也不负责掩盖 485 通信异常。

### 场景六：组合模式的降级与恢复

```text
一个模式目标展开为多个设置项
  -> 后端 HTTP 不可达且所有 settings 确认保存后，形成一组 pending 补丁
  -> 统一刷新先汇总可取得的实际值
  -> 后端可达：保留实际值或最后一次有效值，不使用 pending
  -> 后端不可达：由 pending 补入一次
  -> 完整校验后一次发布 runtime
  -> 后续刷新继续由可取得的实际值驱动
```

组合状态不得由半组新值和无规则的旧值随意拼接。整体成功条件、字段优先级和部分失败策略必须集中
定义；无论组合多复杂，settings、runtime 和 pending 的所有权仍保持不变。
