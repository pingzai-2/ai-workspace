# 运行状态驱动开关显示方案

## 方案定位

本方案把 runtime 视为运行状态 UI 的唯一事实来源。settings 可以保存设置目标或操作记录，但不能用来
推断外部对象此刻的实际状态；只有新的有效 runtime 才能改变运行状态 UI。

本方案适合以下场景：

- UI 必须以外部对象的实际状态为准；
- 外部对象可能被保护逻辑、定时任务或其他控制端改变；
- 多个原始运行字段需要归并为一个状态，或一个实际状态需要影响多个页面；
- 外部数据源能够稳定提供完整、可校验的运行快照。

本方案不适合以下场景：

- 纯 UI 联调要求点击后立即看到状态变化，但没有 runtime 生产者；
- 产品不能接受等待下一份运行快照的反馈延迟；
- 外部数据源无法区分有效值、缺失值和过期值；
- 状态变化频率很高，文件快照无法满足实时性要求。

## 优点与缺点

### 优点

- 外部对象自行停止、故障或被其他控制端改变时，UI 能随下一份 runtime 纠正；
- 设置目标与实际状态明确分离，不把“已经下发”误当成“正在运行”；
- 多个控制来源最终都归一到同一份实际状态，页面显示口径统一；
- 聚合状态可在集中映射层生成，适合一对多、多对一和多对多关系。

### 缺点

- 没有 runtime 生产者时，用户点击成功后 UI 可能看起来完全没有反应；
- 反馈速度受外部读取和刷新周期影响，天然可能晚于设置提交；
- runtime 数据错误、过期或缺失会直接影响显示可信度；
- 为纯 UI 演示人工维护 runtime，操作成本高于 settings 直接驱动方案。

## 1. settings 与 runtime 的数据所有权

| 数据 | 正常写入方 | 负责内容 | UI 使用方式 |
|---|---|---|---|
| settings | 设置或控制提交链路 | 设置目标或最近一次确认的操作 | 不直接驱动运行状态 UI |
| runtime | 运行数据刷新链路 | 当前运行状态和运行快照 | 作为运行状态 UI 的唯一数据源 |

必须遵守：

- settings 与 runtime 分开保存、分开校验、分开恢复；
- UI 不使用 settings 推断当前运行状态；
- runtime 不反向修改 settings；
- 页面不得在控制完成后直接把目标值写成运行状态；
- 多个 runtime 字段可以归并为一个 UI 状态，一个 runtime 字段也可以影响多个 UI 状态；映射集中处理，
  不改变 runtime 的最终显示所有权。

## 2. 何时读取、何时写入

应用启动：

```text
读取 settings
  -> 完整校验
  -> 读取 runtime
  -> 完整校验
  -> settings 初始化设置目标
  -> runtime 初始化运行状态 UI
```

用户提交控制：

```text
锁定当前提交入口
  -> 形成控制目标
  -> 执行控制
  -> 成功后写入 settings
  -> 完整读回并校验 settings
  -> 不直接修改运行状态 UI
  -> 解除提交锁定
```

运行状态刷新：

```text
统一刷新任务触发
  -> 上一轮未结束：跳过本周期
  -> 获取当前运行数据
  -> 汇总形成完整 runtime 候选值
  -> 原子写入并完整读回 runtime
  -> 校验成功后替换内存 runtime
  -> runtime 驱动 UI 更新
```

- settings 不参加 runtime 的周期刷新；
- 控制提交与运行状态显示是两条独立链路；
- 没有有效 runtime 数据源时，控制成功后运行状态 UI 可以暂时不发生变化；
- 运行状态变化只在取得下一份有效 runtime 后显示。

## 3. 原子落盘和读回校验

settings 与 runtime 的每次写入都发布完整文件：

```text
生成完整候选数据
  -> 校验结构、类型、范围和组合约束
  -> 在目标文件同目录写入临时文件
  -> 完成写入并关闭临时文件
  -> 原子替换目标文件
  -> 完整读回目标文件
  -> 再次执行完整校验
```

- settings 读回成功只确认设置记录，不改变 runtime 驱动的 UI；
- runtime 读回成功后，新的运行状态才能替换内存状态并刷新 UI；
- 多个运行数据来源先在内存中汇总，再由统一链路一次发布完整 runtime；
- 不允许只写变化字段、拼接新旧快照或使用 settings 补齐 runtime；
- 读取方只能接受旧的完整文件或新的完整文件。

## 4. 失败、冲突和恢复规则

- 控制失败、settings 写入失败或读回失败：保留上一份有效 settings；
- runtime 获取、写入、原子替换或读回失败：保留上一份有效 runtime 和原 UI 状态；
- 启动时某一份文件不存在或无效：只恢复对应文件，另一份有效文件继续使用；
- 运行中已有有效快照时，一次刷新失败不得发布默认值或半份新数据；
- 同一控制提交尚未结束时，忽略该入口的重复提交；
- 上一次 runtime 刷新未结束时，跳过本周期，不并发、不排队；
- 单个数据读取失败只丢弃自己的本轮结果，不阻断其他独立读取；
- 同一进程内，每份文件只允许一个正常写入链路；
- 多进程或多个应用需要写同一份数据时，必须改由单一协调者负责写入；
- 下一份有效 runtime 始终覆盖旧 UI，settings 中的目标或历史记录不具有显示优先级。

## 脱敏场景示例

以下示例来自某中控屏设备控制项目的通用数据链路，已去除项目名称、设备名称、字段名称、接口、路径和
具体刷新周期，只保留可以复用的机制。

### 场景一：无外部数据源，首次启动

```text
应用启动
  -> 分别读取 settings 与 runtime
  -> 分别校验和恢复
  -> settings 初始化设置目标
  -> runtime 初始化运行状态 UI
```

如果本地 runtime 是默认关闭状态，运行状态 UI 就显示关闭。此后只修改 settings 不会改变该显示。

### 场景二：纯 UI 联调中的控制操作

```text
用户提交开启目标
  -> 控制或模拟控制成功
  -> settings 写入并读回成功
  -> UI 仍显示 runtime 中的旧状态
  -> 联调工具发布新的 runtime
  -> 下一次有效刷新后 UI 才显示开启
```

该行为能严格证明显示来源只有 runtime，但在没有运行数据生产者的演示环境中容易被误认为按钮失效。

### 场景三：外部对象自动停止

```text
settings 中仍保留开启目标
外部对象因保护、定时或达到目标条件而停止
  -> 外部数据源发布实际关闭状态
  -> 统一刷新链路生成并读回新 runtime
  -> UI 显示关闭
```

这正是本方案的主要价值：操作目标可以保留，实际显示仍及时服从运行状态。

### 场景四：控制成功，但实际状态尚未变化

```text
用户提交目标
  -> 控制链路返回成功
  -> settings 保存目标
  -> runtime 暂时仍是旧值
  -> UI 保持旧状态
  -> 取得新的实际状态后再刷新 UI
```

控制成功表示命令被接受或设置已保存，不自动等于外部对象已经完成状态切换。

### 场景五：多个实际值归并为一个模式

```text
统一刷新任务读取一组相关实际值
  -> 所有必需值有效
  -> 映射层按固定优先级识别模式
  -> 一次发布完整 runtime
  -> UI 显示归并后的模式状态
```

必需值缺失时保留上一份有效聚合状态，不用半组新数据推断模式；多个组合同时匹配时必须有固定优先级。
