# 设置状态直接驱动开关显示方案

## 方案定位

本方案把 settings 视为设置状态 UI 的唯一事实来源。用户操作只有在业务确认、完整写入和严格读回均
成功后，才成为新的已确认状态并显示到界面；runtime 继续保存运行快照，但不参与设置状态判定。

本方案适合以下场景：

- 重点是设置结果、配置结果或最近一次确认操作，而不是持续显示外部对象的实际运行状态；
- 外部数据源尚未接入，但需要独立完成 UI、持久化和失败恢复联调；
- 设置状态只有一个正常写入方，且其他控制来源不会绕过该写入方改变显示语义；
- 一个设置意图需要展开为多个字段，或多个已确认字段需要归并成一个设置状态。

本方案不适合以下场景：

- 外部对象可能因保护、定时、故障或其他控制端自行改变状态；
- UI 必须持续、准确地显示当前实际状态；
- 多个应用或进程需要同时写同一份 settings；
- 状态变化频率很高，不能接受文件快照和完整校验的成本。

## 优点与缺点

### 优点

- settings 写入并读回成功后即可刷新 UI，反馈路径短且容易理解；
- 无外部数据源时仍可完整验证点击、保存、重启恢复和失败保持；
- runtime 刷新不会覆盖刚确认的设置状态，两类数据边界清楚；
- 组合设置可集中映射和测试，不要求页面维护零散条件判断。

### 缺点

- settings 记录的是已确认设置，不等于外部对象此刻仍在运行；
- 外部对象自行停止时，如果 settings 没有同步更新，UI 仍会保持原设置状态；
- 存在多个控制来源时，UI 可能晚于外部实际变化，甚至长期不一致；
- 控制提交成功只能证明设置链路成功，不能证明外部对象持续执行该设置。

## 1. settings 与 runtime 的数据所有权

| 数据 | 正常写入方 | 负责内容 | UI 使用方式 |
|---|---|---|---|
| settings | 设置提交链路 | 已确认的设置状态 | 直接驱动对应设置状态 UI |
| runtime | 运行数据刷新链路 | 外部产生的运行快照 | 只驱动运行数据显示 |

必须遵守：

- settings 与 runtime 分开保存、分开校验、分开恢复；
- 设置状态 UI 只接受最近一次有效的 settings；
- runtime 更新不得覆盖 settings，也不得改变 settings 驱动的 UI 状态；
- 页面不得绕过设置提交链路直接修改 settings 文件或已确认内存状态；
- 一个设置意图可以映射多个 settings 字段，多个字段也可以归并为一个 UI 状态；映射集中处理，
  不改变 settings 的所有权。

## 2. 何时读取、何时写入

应用启动：

```text
读取 settings
  -> 完整校验
  -> 读取 runtime
  -> 完整校验
  -> settings 初始化设置状态 UI
  -> runtime 初始化运行数据显示
```

用户提交设置：

```text
锁定当前提交入口
  -> 根据用户意图生成完整 settings 候选值
  -> 执行必要的业务确认
  -> 确认成功后写入 settings
  -> 完整读回并校验
  -> 读回成功后替换内存 settings
  -> settings 驱动 UI 更新
  -> 解除提交锁定
```

运行数据刷新：

```text
统一刷新任务触发
  -> 上一轮未结束：跳过本周期
  -> 获取或读取 runtime
  -> 完整校验
  -> 更新运行数据显示
  -> 不读取、不覆盖 settings
```

运行中的 settings 只在以下时机读取：

- 应用启动；
- 设置提交完成后的严格读回；
- 明确执行整份数据重新加载。

周期 runtime 刷新不负责发现人工修改的 settings。

## 3. 原子落盘和读回校验

settings 与 runtime 的每次写入都发布完整文件：

```text
生成完整候选数据
  -> 校验结构、类型、范围和组合约束
  -> 在目标文件同目录写入临时文件
  -> 完成写入并关闭临时文件
  -> 原子替换目标文件
  -> 完整读回目标文件
  -> 再次执行完整校验
```

settings 还必须校验本次预期修改已经出现在读回结果中。只有全部通过，才能用新 settings 替换
内存状态并刷新 UI。

禁止：

- 先清空目标文件再逐段写入；
- 只写变化字段；
- 用 runtime 补写 settings；
- 写入成功但未读回确认就更新已确认 UI；
- 把两份数据合并为同一写入通道。

## 4. 失败、冲突和恢复规则

- 业务确认、写入、原子替换或读回任一步失败：保留上一份有效 settings 和原 UI 状态；
- runtime 获取或校验失败：settings 不变，设置状态 UI 不受影响；
- 启动时某一份文件不存在或无效：只恢复对应文件，另一份有效文件继续使用；
- 运行中已有有效快照时，一次刷新失败不得用半份数据覆盖上一份快照；
- 同一设置提交尚未结束时，忽略该入口的重复提交；
- 上一次 runtime 刷新未结束时，跳过本周期，不并发、不排队；
- 同一进程内，每份文件只允许一个正常写入链路；
- 多进程或多个应用需要写同一份数据时，必须改由单一协调者负责写入；
- 外部实际状态变化不会自动改变 settings 驱动的 UI。需要持续显示实际状态时，本方案不适用。

## 脱敏场景示例

以下示例来自某中控屏设备控制项目的通用数据链路，已去除项目名称、设备名称、字段名称、接口、路径和
具体刷新周期，只保留可以复用的机制。

### 场景一：无外部数据源，首次启动

```text
应用启动
  -> 分别读取 settings 与 runtime
  -> 分别执行完整校验
       ├─ 文件有效：使用该文件
       └─ 文件缺失或无效：只恢复对应文件
  -> settings 初始化设置状态 UI
  -> runtime 初始化运行数据显示
```

此时 settings 就是设置状态 UI 的可靠来源。某一份文件异常不会连带清空另一份有效数据。

### 场景二：纯 UI 联调中的设置操作

```text
用户点击设置项
  -> 模拟或执行必要的业务确认
  -> 生成完整 settings 候选值
  -> 原子写入并严格读回
       ├─ 成功：替换内存 settings，UI 立即变化
       └─ 失败：保留旧 settings 和旧 UI
```

该场景不要求 runtime 同时变化，因此适合在外部系统尚未完成时验证界面与持久化闭环。

### 场景三：外部对象后来自行改变状态

```text
settings 中的已确认设置：开启
外部实际状态：因保护或定时变为关闭
runtime：记录实际关闭
UI 设置状态：仍显示开启
```

这不是刷新故障，而是本方案的数据所有权结果，也是本方案最重要的缺点。如果产品要求 UI 显示实际
关闭状态，应改用以 runtime 为显示依据的方案。

### 场景四：控制明确失败

```text
用户提交目标值
  -> 外部明确拒绝、超时，或 settings 写入/读回失败
  -> 不发布新的已确认 settings
  -> UI 保留上一次确认状态
```

页面不得先显示目标值再等待失败回滚，否则短暂的错误显示会被误认为操作已经成功。

### 场景五：一个模式对应一组设置

```text
用户选择某模式
  -> 映射层生成多个 settings 候选字段
  -> 所有必需项确认成功
  -> 一次发布完整 settings
  -> 多个已确认字段归并为一个模式 UI 状态
```

如果必需项部分失败，默认保留上一份完整 settings；不要把半组新值与半组旧值拼成一个看似成立的
模式。一对多、多对一和多对多只改变映射规则，不改变 settings 的显示所有权。
