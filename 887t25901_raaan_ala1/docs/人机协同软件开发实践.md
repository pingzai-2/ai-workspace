# 人机协同软件开发实践

## ——以某中控屏项目为例

## 核心观点：人把握框架方向，AI放大执行能力

AI 可以降低代码实现、资料检索和重复验证的成本，但不能替代人对系统方向和整体框架的把握。恰恰因为代码生成得更快，人的架构能力反而更加重要：正确的架构可以让 AI 快速形成有效产出，错误或含糊的架构则会让 AI 更快地扩散错误。

这里所说的架构能力，不只是画模块框图或选择技术栈，而是人在复杂、矛盾和不完整的信息中持续完成以下判断：

- 从产品目标出发，识别系统真正要解决的问题；
- 找出长期稳定的主干与允许替换的实现细节；
- 划分前端、后端、通信、设备和外部服务的责任边界；
- 决定数据由谁产生、由谁保存、由谁解释，避免多个事实源；
- 定义正常流程、异常流程、恢复流程和不可破坏的不变量；
- 判断哪些内容已经确定，哪些内容应保留原始数据、等待证据；
- 选择能够证明结果的测试层级，并承担最终取舍和验收责任。

在本项目中，下面这些都不是编码细节，而是人的架构决策：

```text
一条 TTY 只有一个通信所有者
通信与数据处理分离
HTTP 读取只访问内存快照
控制写入遵守业务互斥，设备读回仍忠实保存事实
后端离线与设备数据陈旧使用不同语义
Wi-Fi 总开关与断开当前网络使用不同命令
前端只面对一份聚合状态，不直接理解底层设备差异
```

这些判断一旦明确，模拟器、后端和前端的大量实现才可以交给 AI 并行展开，而不至于各自形成一套互相冲突的语义。人的作用不是站在 AI 后面逐行检查代码，而是站在系统上方把握方向、建立边界、定义规则，并在证据不足时阻止系统建立在猜测之上。

可以把这种协作关系概括为：

```text
清晰的人的架构 × AI 的执行密度 × 可复现的验证闭环
                        = 可持续的软件交付能力

含糊的人的架构 × AI 的高速生成
                        = 更快扩散的系统性错误
```

本项目要形成的，不是一套只能服务于某个设备或某份协议的代码，而是一套可以替换设备、协议、后端能力和前端技术，同时仍保持数据流、状态语义和验证方法稳定的人机协同工程框架。

例如，具体寄存器地址、设备命令、UI 控件和板端接口都可能变化，但下面这些框架原则可以长期保留：

```text
通信与业务处理分离
命令意向与实际状态分离
写入规则与设备事实分离
底层采集与上层展示通过统一快照解耦
异常状态具有明确语义和恢复路径
每项关键判断都能由测试或实机证据验证
```

这些问题不是多写几个单元测试就会自然解决的。它们首先需要人确定协议边界、业务语义和系统不变量，再由 AI 将判断固化进代码、测试和文档。

所以，更准确的人机分工是：

> 人负责架构、协议边界、业务语义和最终验收；AI 负责实现、检查、构建、仿真和重复劳动。

这也不等于“人完全不看 AI 生成的代码”。人的审查重点应从逐行检查所有实现，转向更高价值的位置：接口是否清楚、状态机是否闭合、不变量是否被守住、数据流是否只有一个事实源、失败是否能够恢复，以及实机结果是否符合产品语义。高风险代码仍应深入检查，低风险和机械性实现则可以更多交给自动测试与工具验证。

我们真正要搭建的，是一套能够反复更换协议、设备和 UI，而核心框架不必推倒重来的工程母版。人的架构能力决定这套母版能否成立，AI 则决定它能以多高的效率被实现、验证和持续演进。

## 1. 为什么要讨论人机协同

AI 已经能够快速阅读代码、生成实现、补测试、执行构建和分析日志，但“能写代码”不等于“能独立完成软件工程”。

一个真实产品通常同时包含：

- 不完整甚至互相矛盾的需求和协议；
- UI、后端、通信、驱动和设备之间的状态协同；
- 并发、超时、重试、掉线和恢复；
- 多平台编译、离线构建和实机部署；
- 无法只靠单元测试覆盖的物理环境。

因此，人机协同的目标不是“把整个项目交给 AI”，也不是“人继续逐行编写和检查所有代码”，而是重新划分工作：

```text
人以架构能力把握方向、边界、语义、风险和验收
AI 负责检索、实现、重复验证和材料整理
文档负责保存共同认知
自动测试负责守住已知规则
实机结果负责作最终裁判
```

某中控屏项目正好是一个典型案例。它包含 Windows 设备模拟器、嵌入式 C/C++ 后端、Flutter 前端、Modbus RTU、多种嵌入式板端能力，以及 macOS、Linux、Windows 和交叉编译环境。单看任何一个模块都不算巨大，但三端协同后，状态语义和系统边界会迅速变复杂。

## 2. 项目背景

当前系统可以简化为下面的数据链路：

```text
模拟器（代替真实设备）
            │
        RS485 / Modbus RTU
            │
            后端
            │
        聚合 HTTP API
            │
        Flutter 前端
```

同时，后端还需要处理不经过 TTY 的本机能力：

```text
TTY 通信       本机设备       系统网络       外部网络服务
   │              │              │                │
Modbus       亮度/指示灯      Wi-Fi          天气/IP等
   └──────────────┴──────────────┴────────────────┘
                          │
                    统一状态快照
                          │
                       HTTP API
```

这意味着一个看似简单的“点击设备控制按钮”，实际上可能跨越：

```text
Flutter 点击
  -> HTTP 命令
  -> 后端业务校验
  -> 写队列
  -> Modbus 写事务
  -> 写后确认读
  -> 后端缓存发布
  -> Flutter 聚合轮询
  -> UI 显示实际状态
```

如果其中任意一层误解了“成功”“已接受”“实际生效”或“离线”的含义，代码即使能够编译运行，产品行为仍然可能是错的。

## 3. 人和 AI 各自负责什么

### 3.1 人的架构能力负责不能外包的判断

在本项目中，人最重要的工作不是敲代码，而是确定下面这些问题：

- 用户点击以后，界面应立即变化，还是等待设备读回？
- HTTP 返回成功表示“设备已执行”，还是仅表示“命令已入队”？
- 多个设备模式之间如何互斥、如何联动？
- 设备实际读回了违反互斥规则的数据，后端应保留事实还是替设备修正？
- “后端离线”和“485 数据陈旧”是不是同一个状态？
- Wi-Fi 总开关和“断开当前网络”是不是同一个动作？
- 某个寄存器定义不明确时，是猜测实现、暂不展示，还是只保存原始值？
- 本机接口失败后，应该回退缓存、保持最后值，还是清零？

这些问题没有可靠的语法答案。AI 可以列方案、分析影响，但最终产品语义必须由人确定。架构能力的价值，就是把这些判断进一步变成可执行的接口、状态、约束和验证标准，让后续实现不再依赖每个人临场猜测。

### 3.2 AI 负责高密度执行

当边界清楚后，AI 很适合完成：

- 从协议、说明书和历史代码中提取字段；
- 查找调用链和影响范围；
- 同步修改模拟器、后端和前端；
- 生成或补充单元测试、边界测试；
- 执行多平台构建；
- 对比日志、帧数据和运行快照；
- 整理文档和提交材料；
- 重复执行大量机械验证。

AI 的优势是速度、耐心和可重复性，不是天然拥有完整产品认知。

### 3.3 文档是人与 AI 的共同记忆

只把架构留在人脑里并不稳健。会话会结束，人员会更换，几个月后原作者也可能忘记当时的判断。

本项目把认知分成几类文档：

- 协议文档：寄存器、位定义、读写属性和数据格式；
- 协议实现清单：哪些已确定、哪些待定、现有实现如何处置；
- 板端能力清单：本机设备、Wi-Fi、亮度、指示灯等已确认能力；
- 后端框架：线程、调度器、缓存、命令队列和快照边界；
- 前端状态融合方案：settings、runtime、pending 和离线退化规则；
- 构建部署文档：不同平台如何离线编译、部署和验证。

因此，更可靠的协作链路是：

```text
人作出判断
  -> 文档固化判断
  -> AI 按文档实现
  -> 测试验证实现
  -> 实机校准判断
  -> 再更新文档
```

## 4. 本项目采用的核心架构

### 4.1 协议像填空题，框架保持稳定

Modbus 通信机制不应随着每个产品协议重新发明。稳定的公共能力包括：

- TTY 独占；
- 请求调度；
- 超时与重试；
- 写优先；
- 异常清理与重新同步；
- 原始寄存器镜像；
- 写后确认读；
- 缓存与 HTTP 快照。

产品差异主要体现在：

- 地址；
- 功能码；
- 数据区间；
- 字段偏移；
- 位定义；
- 缩放和单位；
- 互斥与联动规则。

因此，协议层采用“数据字典/填空模板”的思想：先完整取得原始数据，再按已确认的定义填充结构化字段。未确认的内容保留原始值，不强行创造业务含义。

### 4.2 通信和处理分离

后端和模拟器都遵守相同的边界思想：

```text
通信线程：尽快收发、校验、复制数据
处理线程：解析字段、模拟变化、执行业务规则
状态中心：发布一份完整且自洽的快照
```

这样可以避免慢日志、JSON 组装、网络请求或业务判断占住串口通信。

### 4.3 一个通道只有一个所有者

同一路 TTY 的所有事务都进入同一个调度器线程。周期读、控制写和确认读不能绕过调度器直接访问 libmodbus。

当前通信脉搏可以概括为：

```text
一次只执行一个事务
当前事务完成后重新选择任务
有写任务时优先写
失败允许一次重试
写成功后安排对应区间的确认读
```

这个机制比具体寄存器解释更重要，因为它决定了系统在高频操作、设备超时和异常恢复时是否仍然可控。

### 4.4 实际状态、设置目标和临时意向分离

前端区分三类数据：

| 数据 | 含义 | 能否代表设备实际状态 |
|---|---|---|
| `settings` | 用户设置目标 | 不能 |
| `runtime` | 后端或设备实际运行快照 | 能 |
| `pending` | 后端不可达时的临时离线反馈 | 不能 |

后端可达时，UI 服从实际读回值；后端不可达时，前端才允许使用本地状态进行界面测试。485 异常不等于后端离线：此时保留最后一次有效值，并在连续 30 秒没有成功通信后显示“设备数据陈旧”。

### 4.5 互斥写和设备读回采用不同原则

后端生成控制写时，应执行已确认的互斥和联动规则，并把关联字段组成一次完整的原子组写事务。

设备读回则代表客观事实。即使设备返回的组合违反后端写规则，后端也只做原子事务更新，不替设备修改数据：

```text
控制写：后端整理成符合规则的完整意向
设备读：后端完整保存设备实际返回的事实
```

这是“控制策略”和“状态观测”解耦的关键。

### 4.6 UI 只面对聚合快照

Flutter 不需要知道寄存器、TTY、sysfs 或平台命令。它只做两件事：

```text
读取一份聚合运行快照
提交一个明确的控制命令
```

以后前端换成 Qt、Android 或 LVGL，只要继续遵守同一 API 和状态语义，后端框架不需要推倒重来。

## 5. 模拟器为什么是母版的一部分

模拟器不是简单的随机数程序，而是真实设备的可控替身：

- 使用真实串口接入 RS485；
- 接收与真实设备相同的 Modbus 请求；
- 保持统一寄存器镜像；
- 对合法写入立即响应并支持后续读回；
- 可以周期改变环境数据，用于观察链路是否持续运行；
- 可以动态产生故障、通知和异常状态；
- 可以注入掉线、超时和无效帧等场景。

模拟器让大量联调在真实设备尚未到位时就能进行，也让难以稳定复现的异常变得可重复。

但模拟器通过不等于实机通过。串口转接器、电气干扰、驱动行为、系统资源和真实设备内部时序，仍必须在实机阶段验证。

## 6. 一次可靠的人机协同开发流程

### 第一步：建立事实，不急着写代码

```text
读取协议和产品说明
查看现有提交与历史实现
探测实际系统和设备能力
区分已确定、待确认和明确错误
```

现有提交是母版。协议待定不等于删除现有实现；只有明确证明错误时才回退或修正。

### 第二步：由人确定不变量

不变量是无论代码如何实现都必须成立的规则，例如：

- 同一路 TTY 只能有一个通信所有者；
- HTTP 读取只读缓存，不进入底层设备；
- 写失败不能修改实际状态缓存；
- 组合确认读不完整时不能发布半组状态；
- Wi-Fi 关闭与普通断开必须是不同语义；
- 设备读回不能被后端互斥策略篡改；
- 未确认字段不得凭空增加业务含义。

AI 可以帮助补充边界，但不应自行改变这些规则。

### 第三步：拆成可以验证的小任务

一个任务应包含：

```text
明确输入
明确输出
允许修改的模块
不允许改变的行为
可以执行的验证方式
```

例如“实现设备模式控制”不能只写成一个模糊目标，而应拆成：

1. 模拟器接受寄存器写入并按规则更新统一镜像；
2. 后端校验互斥条件并生成原子组写；
3. 写成功后精确确认读；
4. 聚合快照发布实际状态；
5. 前端提交命令并在可调延迟后补读；
6. 后端离线时保留 UI 测试能力；
7. 三端联调验证开、关、超时和恢复。

### 第四步：AI 实现，人检查高风险边界

不是所有代码都需要同等强度的人工审查。

高风险区域应重点检查：

- 协议解析、CRC 和字节序；
- 线程、锁和队列；
- 状态所有权与原子更新；
- 设备写操作和失败回退；
- 持久化和恢复；
- 构建、部署和启动脚本。

普通字段映射、重复接口封装和测试样例可以更多依赖自动检查。

### 第五步：分层验证

```text
静态检查
  -> 单元测试
  -> 模块构建
  -> 模拟器与后端联调
  -> 模拟器、后端、前端三端联调
  -> 目标板端实机验证
  -> 长时间和异常场景验证
```

必须准确描述证据：

- “编译通过”只证明能生成产物；
- “模拟器联调通过”只证明当前模拟链路；
- “主机 Debug 正常”不等于嵌入式板端正常；
- “板端启动成功”不等于业务逻辑正确；
- 实际设备的通信、驱动和交互结果才是最终验收依据。

### 第六步：小步提交和可回退

依赖、构建脚本和业务母版可以分批提交，避免一次提交混合大量不同性质的改动。临时分支用于隔离工作，合入后及时清理；提交信息应能说明改了什么和为什么。

Git 记录不是形式工作，它让团队能够：

- 精确定位回归来源；
- 单独回退某类修改；
- 区分依赖、构建和业务变化；
- 复核 AI 是否越过任务边界。

## 7. 本项目已经验证的典型经验

### 7.1 语法正确不等于语义正确

Wi-Fi 总开关和“断开当前 Wi-Fi”都可能调用断开命令，但产品语义完全不同：前者关闭能力，后者仍允许扫描和重新连接。只有人先说清楚状态机，AI 才能实现正确。

### 7.2 写成功不等于状态已经改变

Modbus 写请求成功，只表示本次写事务成功。UI 显示的实际状态还需要设备读回。后端增加写后确认读，前端增加可调的一次性补读，可以缩短反馈时间，但不能用用户意向冒充设备事实。

### 7.3 自动测试不能发现未表达的需求

如果测试只验证“断开命令被调用”，它无法发现 Wi-Fi 开关和普通断开的语义混淆。测试必须由不变量和场景驱动，而不是只覆盖代码分支。

### 7.4 多平台构建必须使用真实环境证据

同一份源码需要在 macOS、Linux、不同嵌入式板端和 Windows 模拟器环境中工作。主机构建通过不能替代交叉编译；交叉编译成功也不能替代板端动态库、文件系统和启动方式验证。

### 7.5 简洁来自正确分层，不是减少必要机制

写队列、确认读、状态缓存和过程管理器看似增加代码，但它们让每层职责更单一。真正应避免的是隐式副作用、多份互相冲突的数据源，以及页面直接操作协议或系统命令。

## 8. 常见误区

### 误区一：使用最强模型就不需要架构

模型越强，越可能生成一套看起来完整的方案。如果输入边界不清楚，它也可能更完整地实现错误方向。

### 误区二：测试通过就不需要人工判断

测试只能验证已经表达的规则。协议误解、遗漏场景、物理设备差异和错误产品语义仍需要人工判断与实机验证。

### 误区三：所有思考只留在人脑里

人应保留最终决策权，但决定必须写成可复查的文档和测试。否则项目会依赖个人记忆，AI 也无法稳定复用上下文。

### 误区四：多智能体自然等于高质量

多个 AI 可能同时重复同一个错误。真正有效的是角色分离：实施者、审查者和测试者采用不同检查视角，并共同服从同一份事实和验收标准。

### 误区五：为了未来扩展提前抽象一切

母版需要稳定边界，但不需要为尚未出现的需求构造复杂框架。先建立一个可运行、可测试、可替换的朴素版本，再根据真实扩展点演进。

## 9. 可复用的协作检查表

### 开始前

- 当前事实来源是什么？
- 哪些内容已确定，哪些只是推测？
- 是否存在不能破坏的现有行为？
- 本轮允许修改哪些模块？
- 完成标准能否实际验证？

### 实现中

- UI、业务、协议、缓存和平台层是否仍然分离？
- 是否出现第二份业务真值？
- 锁内是否只做快速、有限的工作？
- 失败路径是否保持上一份确认状态？
- AI 是否增加了没有需求依据的功能？

### 验证时

- 正常路径、失败路径和恢复路径是否都覆盖？
- 是否验证连续点击、并发、超时和掉线？
- 模拟器与真实设备的边界是否说清楚？
- 构建证据来自哪个平台？
- 是否把“能运行”误写成“逻辑正确”？

### 交付前

- 文档是否与当前代码一致？
- 提交是否只包含本任务内容？
- 是否保留临时文件、备份文件或生成物？
- 是否能够单独回退？
- 实机未验证的内容是否明确标出？

## 10. 结语

AI 时代的软件工程并没有让基础能力过时，反而放大了基础能力的价值。AI 可以把一个决定迅速扩展成大量代码，也可以把一个错误理解迅速扩散到整个系统。

因此，人的价值正在从“亲手完成所有代码”转向：

```text
理解系统本质
划定责任边界
定义状态和不变量
选择验证证据
承担最终决策
```

AI 的价值则是：

```text
快速理解材料
执行边界明确的任务
完成高密度重复劳动
持续构建、测试和校验
把人的设计稳定落地
```

这个中控屏项目所形成的母版，不只是某一份具体协议的实现。它更重要的成果，是一套可以替换设备、协议、后端能力和前端技术，同时仍保持数据流、状态语义和验证方法稳定的人机协同工程框架。

最终目标不是让人退出开发，而是让人把精力集中在真正不可替代的地方：

> 人把握框架，AI提高执行密度，文档保存认知，测试守住规则，实机验证现实。
