# 页面生命周期与按需刷新机制说明

## 1. 文档定位

本文是一份可以单独实施的页面生命周期与刷新方案，合并了“页面生命周期与 OnTick”及
“页面按需刷新”两部分内容。它面向嵌入式设备 UI，也可供其它 Flutter UI 工程参考，
不绑定具体屏幕尺寸、设备型号、页面名称或项目类名。

本文中的 `onEnter/onTick/onLeave` 是业务职责名称，不要求页面额外声明同名接口。实现时可优先
使用 Flutter 原生的挂载、`initState()`、`dispose()`、状态通知和异步任务表达这些职责。

## 2. 核心结论

```text
一个普通业务轮询源
  -> 得到一份最新完整业务快照
  -> 判断当前页面或页面范围是否需要刷新
  -> 发布状态变化
  -> Flutter 被动安排 build
```

必须遵守：

- 不使用 `IndexedStack` 长期挂载所有完整页面；
- 普通页面不各自创建两秒 JSON 轮询器；
- 定时器不直接调用 `build()`；
- 上一轮刷新尚未结束时跳过本周期，不排队；
- 页面离开后释放自己的 Timer、Ticker、Controller、FocusNode、Overlay 和异步回调所有权；
- 工程模式暂停普通 runtime 链路；
- 息屏时间使用独立轻量时钟，不写入 JSON；
- 读取失败不应用半份数据，不覆盖上一份已确认快照。

## 3. 页面生命周期

### 3.1 页面是独立的挂载单元

完整页面、设备页、设置页和工程页都应能独立进入、离开和释放。页面之间可以复用无状态控件、
数据模型和服务，但不能通过长期保留所有页面实例来复用状态。

模糊背景弹窗属于允许的临时组合：当前背景页可以在 `AbsorbPointer` 下与前景弹窗短暂同时挂载，
但它们共同组成当前唯一活动界面，不能演变成多个完整业务页面长期后台运行。

### 3.2 业务职责与 Flutter 生命周期的对应

| 业务职责 | Flutter 中的当前承载方式 |
|---|---|
| `onEnter` | 新页面挂载、入口令牌变化、`initState()`、一次性数据初始化 |
| `onTick` | 统一调度器更新快照，再通过 `ValueNotifier` 或根状态通知当前界面 |
| `onLeave` | 页面从当前子树移除、入口令牌失效、`dispose()` 和异步结果丢弃 |

不要为了形式统一增加空的生命周期接口。只有多个页面确实出现相同调度需求时，才从现有实现中
提炼公共抽象。

### 3.3 页面切换顺序

推荐顺序：

```text
旧页面继续显示
  -> 准备目标页数据和首屏资源
  -> 校验导航请求仍然有效
  -> 切换当前页面
  -> 目标页开始接收业务更新
  -> 旧页从子树移除并释放局部资源
```

目标页准备期间不得响应用户输入，也不得启动第二条业务轮询。

## 4. 页面加载模式

页面加载策略描述的是切换期间旧页和目标页的资源关系：

```dart
enum PageLoadMode {
  releaseThenLoad,
  preloadPartialThenRelease,
  preloadAllThenRelease,
}
```

- `releaseThenLoad`：先释放旧页再加载目标页，内存最低，但可能短暂黑屏；
- `preloadPartialThenRelease`：先准备首屏关键资源，允许超时后使用页面自身加载兜底；
- `preloadAllThenRelease`：目标页首帧需要的全部资源准备完成后再切换，视觉最稳定，但峰值内存最高。

工程不必强制使用同一种模式。必须以实际代码、页面资源和设备内存为准，不能在文档中把
“分批预加载”误写成“所有资源都已完成”。启动页、普通内页和大型设备页也可以分别选择
不同模式，但选择结果应明确记录并可通过首帧和内存测试验证。

## 5. 统一周期调度

### 5.1 非重入流程

```text
两秒定时器触发
  -> 当前刷新任务正在执行：跳过本周期
  -> 当前空闲：开始一次刷新
      -> 获取外部或本地 runtime 数据
      -> 校验并形成完整业务快照
      -> 成功才替换内存状态并发布
      -> 失败保留上一份状态
  -> 释放“刷新中”标志
```

参考伪代码：

```dart
Future<void> refreshRuntime() async {
  if (refreshInFlight || specialModeActive) return;
  refreshInFlight = true;
  try {
    final next = await repository.refreshRuntime(current);
    publish(next);
  } finally {
    refreshInFlight = false;
  }
}
```

这里的“快进快出”是指调度器不在 UI 线程同步阻塞设备调用；异步刷新本身允许超过两秒，下一周期
直接跳过即可。

### 5.2 一份统一业务快照

页面只消费已经准备好的 `DashboardData`，不知道 JSON 路径，也不区分字段来自 settings 还是
runtime。数据所有权仍由各数据规约定义；刷新层只负责发布最终可显示快照。

## 6. 两种合法的按需刷新粒度

### 6.1 当前页面级刷新

只挂载当前页面时，根协调器可以在 runtime 更新后替换统一快照并 `setState()`。这样会重建当前
页面，但不会重建已经离开的页面。适合页面较小、刷新成本可控的设备。

这种方式适合只挂载当前页面、页面规模较小且刷新成本可控的工程。

### 6.2 页面范围级刷新

页面较大或字段较多时，可以为主页、智能、手动、历史、设置、息屏和弹窗分别建立通知通道，
通过刷新签名判断字段变化是否真正影响该范围：

```text
新旧快照比较
  -> 相关页面签名变化：发布新快照
  -> 页面没有使用的字段变化：不发布
```

这种方式适合页面较大、字段较多或需要严格控制重建范围的工程。页面范围通知器只是发布通道，
完整状态仍以根协调器保存的统一快照为准。

新增 `DashboardData` 字段时，应按“最终影响哪些界面元素”登记刷新范围。公共右侧状态栏使用的
`timeFormat` 和 `wifiConnected` 属于所有普通页面的间接依赖；左侧主页内容不因此变成公共依赖。

历史趋势接入统一脉搏，但不另建页面轮询：主脉搏每次累加历史计数，计数达到 10 后尝试
读取 day/week/month。计数采用大于等于 10 的饱和判断；请求正在进行时本次跳过且不清零，
下一个脉搏继续尝试，直到请求成功发起。历史请求结果暂存到同步层，下一次 runtime 原子写入
时按时间戳映射到现有槽位；有效桶局部更新，`null` 或异常桶保留旧值，历史失败不影响实时快照。

## 7. Flutter 被动构建边界

```text
协调器修改状态或 notifier.value
  -> Flutter 将相关 Element 标记为需要重建
  -> Flutter 在合适帧调用 builder/build
  -> 页面读取新快照并描述界面
```

允许页面使用 `setState()` 处理按钮按压、草稿、滚轮、弹窗和动画等局部状态。禁止页面为了刷新
业务 JSON 自建重复轮询器，也禁止手动调用 `build()`。

## 8. 工程模式、产测与息屏

### 工程模式和产测

- 普通 runtime 轮询保持单一来源，但特殊模式期间必须提前返回；
- 工程编辑先保存在内存中，明确确认后才写 `dashboard_persistent.json`；
- 退出特殊模式时重新读取完整数据，再恢复普通页面；
- 特殊模式可以有自己的局部超时或产测步骤，但不能启动第二条主页 JSON 轮询。

### 息屏

- 业务页无操作达到设定时间后进入 Idle 页面；进入 Idle 后再连续 30 秒无触摸，先显示
  `Color(0xFF000000)` 纯黑帧，再调用后端 `POST /setScreenSleep` 息屏；
- 息屏命令只负责发出，不以返回值分支界面；黑屏后保持纯黑画面，兼容无后端模拟端；
- 硬件已经息屏时，首次触摸先调用 `sleep:0` 唤醒，黑屏保持到一帧完成后再显示 Idle，
  用于清除唤醒瞬间可能残留的画面；唤醒返回值不参与界面分支；
  息屏前的 Idle 触摸仍返回进入息屏前的业务页；
- 环境数据复用统一业务快照；
- 时间来自 `TimeSource` 和独立轻量 Timer；
- 页面销毁或离开 Idle 时停止息屏 Timer，并使未完成的唤醒/息屏结果失效。

## 9. 新页面接入清单

- [ ] 明确数据来自 runtime、settings、persistent 还是纯内存；
- [ ] 不新增第二条普通业务轮询；
- [ ] 明确当前页面级刷新是否足够，或需要加入页面刷新签名；
- [ ] 页面进入前的数据和首屏资源条件明确；
- [ ] 页面离开后 Timer、Ticker、Controller、FocusNode、Overlay 和异步回调不再存活；
- [ ] 工程模式和产测不参与普通 runtime 链路；
- [ ] 读取失败不覆盖上一份完整快照；
- [ ] 公共控件使用的字段加入所有相关刷新范围；
- [ ] 新增测试证明相关页面会刷新、无关页面不会被误刷新。


## 10. 工程核验方法

核验其它 UI 工程时，按下面顺序从源码取证，不按类名猜测：

1. 搜索 `Timer.periodic`，确认普通业务轮询源数量；
2. 检查异步刷新开始前是否设置非重入标志，是否在 `finally` 中释放；
3. 检查页面是否直接读取 JSON，或创建了重复业务定时器；
4. 检查根页面是只挂载当前页，还是用 `IndexedStack` 长期保留全部页面；
5. 检查预加载是否有超时兜底，并据此准确判断加载模式；
6. 检查工程模式、产测和息屏是否遵守各自的数据与 Timer 边界；
7. 检查每个局部 Timer、Ticker、Controller、FocusNode 和 Overlay 的释放路径；
8. 若使用页面刷新签名，检查公共控件的间接字段依赖是否登记完整；
9. 用慢读取、快速切页、重复进入退出和长时间运行测试验证结论。
