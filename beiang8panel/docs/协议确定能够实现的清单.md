# 协议确定能够实现的清单

> 母版实现版：2026-08-21
> 当前依据：`4CP-全热新风-主控对外通讯协议v1.21`、`4CP-8寸控制面板软件开发说明-V1.3.1-0810.xlsx`、模拟器/后端/8寸 App 当前源码。
> 本文中“已实现”指三端源码母版已闭环；不等于真实 4CP/R818 实机验收。

## 1. 范围和判定原则

本文只处理 4CP / 全热新风的 Modbus RTU 协议链路：

```text
4cp-simulator（从机） <-> RS485 <-> BeiAng8Panel（主机） <-> HTTP <-> 8寸 App
```

R818 本机温湿度、雷达、AQI 灯、屏幕、Wi-Fi、扬声器、天气等非 TTY 能力，单独记录在《板子确定能够实现的清单.md》，不混入本协议表。

判定规则：

1. 线上地址、功能码、字节顺序、寄存器含义以 v1.21 协议为准。
2. UI 显示和交互要求以 V1.3.1 PRD 为准，但不能反推协议中没有写明的单位、枚举或状态。
3. 当前代码只用于标记“已经做到哪里”，不能替代协议成为事实来源。
4. 协议写明且没有冲突的字段，列入“确定可实现”。
5. 地址已知但语义、单位或枚举不完整的字段，只捞原始值，不进入业务判断。
6. 预留、待补充、文档互相冲突的字段保留位置，不猜含义。
7. 可以多捞数据，但业务层只消费已经确认的字段。

### 1.1 现有提交的增量校准原则

当前讨论和后续实现都以现有提交为母版，只做增量校准，不因协议仍有待确认项就重做或删除已有能力：

1. **现有实现存在、但协议暂时不能确认**：保留现有协议等效行为，同时保存原始值并标记待确认。例如 RTC 排列仍待校准，现有实现先保持。
2. **有明确证据证明现有实现错误**：才修改现有逻辑，并记录错误依据及行为变化。例如超净字段或接口映射确认错误后，统一修正模拟器、后端和 App。
3. **协议已经确认、现有实现缺失**：在原结构上新增，不破坏其他已有能力。例如补充 1001H/1002H/1003H 互斥、1000H 自动联动和后端写入条件检查。
4. 判断顺序固定为：先看现有提交是否已有实现，再判断是否有明确错误证据；没有明确错误就保留，确认缺失的能力再新增。
5. 清单同时记录“协议确定程度”和“现有实现处置”，避免把“待确认”误写成“必须回退”。

状态说明：

- **确定**：协议结构、地址和业务含义足够明确，可以直接实现。
- **原始保留**：可以稳定收发和保存原始值，但暂不解释业务含义。
- **待确认**：存在冲突、缺字或实机相关问题，暂不进入正式业务。
- **当前已做**：仅表示源码已有对应路径，不代表实机验收通过。

## 2. 三端统一的数据填空方式

### 2.1 统一思想

三端使用同一份逻辑数据字典：

```text
通信层收帧
  -> 填原始 uint16_t 字区 / 位区
  -> 按固定地址偏移填业务字段
  -> 业务层只读业务字段
```

建议的原始数据基准：

```c
uint16_t holding_words[0x41];  /* 1000H..1040H，共65字 */
uint16_t input_words[0x5C];    /* 2000H..205BH，共92字 */
uint16_t discrete_words[5];    /* 位0..76，按16位归并 */
```

- 03/04 返回值先由通信层解成主机端 `uint16_t`，再按 `地址 - 起始地址` 取数。
- 02 返回的 bit 先由一个内联函数填入 `discrete_words[bit / 16]`，业务层不直接处理 Modbus 打包字节。
- C/C++ 两端可以共用相同的地址常量、枚举和结构布局；Dart 端保留相同字段名和枚举值。
- 不能把 RTU 原始字节直接 `memcpy` 到 C 结构体，因为线上字节序、结构体对齐和位域布局不等价。可以在通信层解码后，再像泉峰工程一样按固定偏移快速填结构。

推荐的 02 位操作只保留两个小内联函数：

```c
static inline void bit_word_set(uint16_t *words, uint16_t bit, uint8_t value)
{
    const uint16_t mask = (uint16_t)(1u << (bit & 15u));
    uint16_t *word = &words[bit >> 4];
    *word = value ? (uint16_t)(*word | mask) : (uint16_t)(*word & ~mask);
}

static inline uint8_t bit_word_get(const uint16_t *words, uint16_t bit)
{
    return (uint8_t)((words[bit >> 4] >> (bit & 15u)) & 1u);
}
```

### 2.2 三端各自职责

| 端 | 确定职责 | 当前情况 |
|---|---|---|
| 模拟器 | 保存寄存器镜像；收到合法请求后立即读/写镜像并应答；数据变化逻辑在独立处理线程执行 | 已实现进程 + 从机调度器；02/03/04/06/10 共用同一镜像；06/10 写入可被后续 03 原样读回 |
| 后端 | 独占 TTY；周期采集原始字区；写任务优先；通信与解析分离；对 App 提供语义 API | 65 字保持、92 字输入、3 段离散量均已采集；原始区和语义结构在同一次发布中更新；写入只进入唯一 TTY 调度队列；任意一次真实 Modbus 读或写成功都重置 30 秒单调计时窗口，达到 30 秒仍无成功通信才令 `dataFresh=false`，不暴露缓存时间 |
| 8寸 App | 不感知 TTY、从站地址和寄存器；约每 2 秒读取后端运行快照；控制只提交业务意图 | 已收口为一次聚合 GET，总超时 500ms；仅把缓存有效的室内/室外环境、已确认故障和现有 IEF 样板字段填入 runtime；区分后端不可达与设备数据陈旧，并保留最后一次有效值 |

| 项目 | 确定内容 | 当前实现 |

| 字数据顺序 | 一个寄存器内部高字节在前、低字节在后 | libmodbus/模拟器已按标准寄存器字序处理 |

### 3.1 地址识别

首次通信可以只做两个固定地址的问答，不做全地址扫描：

1. 向 `D1H` 发送一条合法读取。
2. 向 `C1H` 发送同样的合法读取。
3. 谁返回有效 Modbus 响应，本进程就选择谁。
4. 两者都不响应则报告离线；两者都响应则报告地址冲突，不自行选择。

建议问答读取 `2000H..2002H`，这样同一帧顺便取得 `BA`、机型和版本，但“谁应答地址就是谁”才是首要识别条件。后端当前尚未自动执行这两个地址的问答。

### 3.2 CRC 确定边界

- 已根据客户实际代码确认：CRC16 使用标准 Modbus RTU 线路顺序，低字节在前、高字节在后。
- 当前 v1.21 协议文档中的 CRC 字节顺序与实际代码不一致，待客户后续版本修正文档。
- 模拟器和后端均直接使用 libmodbus 标准 CRC 行为，不启用自定义顺序兼容项。

### 4.3 离散输入

离散输入不必把未定义的空洞一次读完，初版按有效区间分三次读取：

| 位区间 | 数量 | 内容 | 当前后端 |
|---|---:|---|---|
| 0..6 | 7 bit | 设备能力 | 已按有效段周期读取并填入统一位字区 |
| 32..35 | 4 bit | 设备运行状态 | 已按有效段周期读取并填入统一位字区 |
| 64..76 | 13 bit | 故障状态 | 已按有效段周期读取并填入统一位字区 |

PRD 对其中两组字段又给出了产品默认值和显示要求，但不改变协议字段本身的含义：

- `1025H` 默认开启，`1026H` 的产品默认值为 60 分钟，`1027H` 的产品默认值为 2 分钟。
- PRD 另要求关机检测时采用“全热/低档”，但 `1025H..1027H` 只能表达开关、间隔和运行时间；模式/档位如何下发是策略层问题，不用这三个字段猜测。
- PRD 把滤网寿命以“天”显示，协议 `1031H..1035H` 以“小时”传输。小时转天时的取整规则尚未规定，不先写死。
- `1031H..1033H` 只命名为滤网1/2/3；PRD 使用初效/中效/高效名称。两者对应关系确认前，后端保留编号字段，App 不自行对号。
- `1036H` 是“整机保养剩余天数”，`2026H` 是外部设备“系统累计运行天数”。若PRD的“设备已稳定运行 xxx 天”指4CP，则 `2026H` 是候选来源；若指控制屏，则应由本机运行统计提供。无论哪种含义，都不能用 `1036H` 剩余值代替。
- 维护页的“重置滤网周期”不是写 0。它应在二次确认后，把工程配置中的完整寿命重新写入对应 `1031H..1035H`，再等待周期读取验证；完整寿命的配置来源和滤网名称映射确认前不开放正式写入。
- 整机保养重置同理：应把工程配置的下一次保养天数写入 `1036H`。它不清零 `2026H` 系统累计运行天数，也不等同于 `103FH` 清除风机累计时间。

### 5.2 已确认的控制联动与 UI 边界

模块总开关和三个模块开关按下面的确定关系处理：

```text
1000H = (1001H != 0 || 1002H != 0 || 1003H != 0) ? 1 : 0
```

- 1001H 新风与 1003H 调湿相互独立，可以同时开启。
- 开启 1002H 超净时，后端写策略同时关闭 1001H、1003H。
- 开启 1001H 时，后端写策略关闭 1002H，不改变 1003H。
- 开启 1003H 时，后端写策略关闭 1002H，不改变 1001H。
- 三个模块全关时 1000H 自动为 0；任一模块开启时 1000H 自动为 1。
- 协议设备本身会联动 1000H，因此后端不必重复写 1000H；模拟器必须实现相同联动。

“一键离家”在本协议范围内的确定目标是只开新风：

```text
1001H..1003H = [1, 0, 0]
```

新风页面当前确认的控制映射：

| UI 操作 | 后端写入目标 |
|---|---|
| 内循环 | 1006H=0，1007H=0 |
| 全热交换 | 1006H=0，1007H=2 |
| 自动 | 1006H=1；1007H、1008H改为只读，不主动写 |
| 风速 L1..L5 | 1008H=1..5；实际最大档位还要受机型和 2003H/2004H 限制 |

初版 UI 可以不提前禁用无效操作，但后端必须兜底：

- 1001H=0 时拒绝 1006H..1008H 写入。
- 1006H=1 时拒绝 1007H、1008H 写入。
- 被拒绝的操作不能修改实际状态缓存，也不能让 UI 保留虚假的目标状态。
- UI 不维护互斥表，不根据一次写响应推导其他按钮；所有页面和按钮统一展示后续聚合读取到的实际状态。
- 上述互斥由 4CP 设备按协议执行，后端对模块开关只下发对应的单寄存器写（`1001H`/`1002H`/`1003H`）。设备周期读或确认读即使返回不符合互斥关系的 `1001H..1003H`，后端也把完整读回作为一次“原子事务更新”，按设备实际值同时发布原始镜像和业务字段，不在读取、解析或缓存层纠正。

| 2026H | 系统累计运行时间 | 天 |
| 2027H..202AH | FAN1..4 累计运行时间 | 小时 |
| 202BH..2042H | 4 个风机 × 6 档风量表 | `uint16_t fanFlow[4][6]` 原样保存；单位未写明，不换算、不在 UI 标注单位 |
| 2043H..2045H | 阀门1..3状态 | 0=关、1=半开、2=全开 |
| 2046H..2048H | 风阀1..3方向 | 保存 `uint16_t` 原值 0/1；方向名称未写明，不解释为正向/反向 |
| 2049H..204BH | 风阀1..3运行步数 | `uint16_t` 原样保存；单位和清零规则未写明 |

仅原始保留：

| 地址 | 原因 |
|---|---|
| 2002H | 示例为 `0101`，但十六进制/BCD/十进制版本编码规则未明确 |
| 201DH..2023H | 预留 |
| 2024H..2025H | 只写明 Bit0/1/2，三个浮子位的分别含义未展开 |
| 204CH..204FH | 明确为预留；只保留原始寄存器值，当前后端把它们放入字符串结构的语义需要移除 |
| 2050H..205BH | 确定是 `Char[24]`、不足补 `0x00`；暂存为 12 个原始字/24 个原始字节，业务含义、编码和每字内字符顺序未写明 |

### 6.1 `2000H..202AH` 已确认的实现边界

1. `2000H` 的 `BA`、`2001H` 的机型和合法 Modbus 应答都可以作为设备识别信息；地址探测仍以 `D1H`/`C1H` 谁返回合法应答为首要条件。
2. `2002H` 只确定示例值为 `0101`，版本编码方式不明确。现有解析行为保留，新数据字典必须同时保存 `uint16_t` 原值，不增加版本判断。
3. `2003H`/`2004H` 是新风模式、内循环/混风模式的最大档位，可作为 `1008H` 写入范围的设备能力来源；读取失败时保留现有档位逻辑，不能因此使原有控制全部失效。
4. `1008H` 是用户设置/设备控制档位；`2005H..2008H` 是四个风机各自实际档位；`2009H..200CH` 是四个风机实际转速。三类数据不能合并成一个字段，UI 没有四风机详情页时可以只缓存不展示。
5. `200DH..2018H` 依次保存 RA1、OA、SA 三组温度、湿度、PM2.5、CO2。温度按有符号值除以 10，湿度按 0..100，PM2.5/CO2 保存原值；现有室内/室外映射继续保留，SA 暂无页面也正常进入数据字典和缓存。
6. `2019H` TVOC、`201AH` 甲醛的单位和比例未写明。现有提交已有的显示效果保留，同时保存原值，不能仅因协议缺少单位就删除。
7. `201BH` 压缩机运行频率只保存原值；`201CH` 是电辅热实际状态，和 `1013H` 设置目标分开保存。
8. `201DH..2023H` 只保留原始值。`2024H`/`2025H` 保存完整 `uint16_t` 浮子位图；现有处理可以保留，但在三个 bit 的逐位含义确认前不新增业务告警名称。
9. `2026H` 保存系统累计运行天数，`2027H..202AH` 保存四个风机累计运行小时数。恢复出厂后的清零结果只认设备后续读回，前端不自行清零。

### 6.2 `202BH..205BH` 本批实现边界

1. 模拟器保留完整寄存器镜像，未产生业务数据时可填 `0`。
2. 后端现有两段输入寄存器读取已覆盖本区间，风量、阀门、方向和步数的寄存器偏移也已接入。
3. 后端数据结构中风量、方向和步数的旧地址注释需要按 `202BH..204BH` 校正。
4. `204CH..204FH` 不能作为设备字符串解释；只进入原始寄存器缓存。
5. `2050H..205BH` 在用途、编码和字节顺序确认前不转换为业务字符串。
6. 8 寸 App 当前没有对应业务展示，本批数据暂不接 UI，不影响采集和缓存。

### 7.4 主页故障弹窗与通知弹窗

8 寸 App 主页现有“故障”和“通知”两个独立入口。PRD 已经确定两者的基本交互，但它们的数据来源不同。

#### 7.4.1 故障列表

1. 故障弹窗只展示后端运行快照中已确认的 bit 64..76，跳过待补充的 bit 67。
2. 有故障时主页故障图标红色高亮；无故障时不显示故障图标。
3. 点击故障图标打开弹窗，同屏最多显示 4 条，超出部分下拉滚动；点击弹窗外关闭本次界面。
4. 故障出现和消失都只认设备后续读回值。PRD 的“更新后清除故障代码”按重新采集后该 bit 消失理解，不是 App 写一条“清故障”命令。
5. 关闭弹窗不向设备写数据，也不从后端缓存删除故障。通信暂时中断时保留最后有效故障列表，并由 `dataFresh=false` 表达数据陈旧。
6. 处理建议和售后电话是 UI/本机配置元数据，不在 bit 64..76 中。故障代码可以映射固定中文描述，服务商电话待本机工程配置落地后提供。
7. PRD 只说“严重故障”触发物理 AQI 红色呼吸灯，但严重故障与 bit 的关联清单仍缺失。未确认前不把所有故障都视为严重故障。

#### 7.4.2 通知列表

1. 通知不是 Modbus 故障位。铃铛始终显示，角标显示未确认数量；点击打开通知弹窗，同屏最多 4 条，超出部分滚动，点击弹窗外关闭。
2. 每条通知显示日期和“确认”；确认后只从**本次已经打开的通知弹窗**中临时隐藏。关闭弹窗后临时确认集合销毁；如果后端下一次仍返回同一通知，再次打开弹窗仍然显示。这个动作不清零寄存器、不重置滤网寿命。
3. PRD 确定的通知来源为：
   - IEF 和初效滤网清洁提醒：剩余周期不大于 15 天后，每天提醒 1 次；
   - 中效、高效滤网及加湿模块寿命提醒：剩余周期不大于 15 天后，每天提醒 1 次；
   - 系统稳定运行天数：每周提醒 1 次。
4. 滤网/模块提醒可以由 `1031H..1035H` 剩余小时生成；“稳定运行天数”要先确认指外部4CP还是控制屏，候选来源分别为 `2026H` 和本机运行统计。滤网1/2/3 与初/中/高效的对应、小时转天取整仍需定稿。
5. 通知、故障的入口、列表、数量和清除语义分别维护，不能互相覆盖、互相清除或从彼此推导。
6. PRD 未要求新故障或新通知必须自动打断当前页面，初版仍由用户点击图标查看；自动弹出和提示音不自行增加。
7. 本轮不实现通知历史、不实现已读状态持久化，也不实现跨轮询、跨弹窗或跨重启的通知去重。后端每次只返回当前条件下成立的通知集合，前端不把它累计成历史消息。

#### 7.4.3 本轮三端闭环和动态变化策略

本轮把故障和通知作为通信链路测试数据贯通，但不把随机测试逻辑带入正式业务判断：

| 层级 | 故障 | 通知 |
|---|---|---|
| 模拟器 | 在已确认的 bit 64..76 中随机置位/清零，跳过 bit 67 | 随机改变 `1031H..1035H` 等维护剩余值，使通知条件能够出现和消失；不直接制造 App 文案 |
| 后端 | 读取当前故障位，映射成当前有效故障列表并放入聚合快照 | 根据当前寄存器/运行数据生成当前有效通知列表并放入聚合快照；本轮不保存通知历史 |
| 8寸 App | 主页故障图标和已经打开的故障弹窗都跟随后端当前故障列表 | 主页铃铛常驻，角标跟随后端当前通知列表；通知弹窗在打开瞬间取得一份列表快照，打开期间冻结，只响应本次弹窗内的“确认” |

动态变化按下面的行为执行：

1. **没有打开弹窗时**
   - 故障从无变有：主页出现故障图标，但不自动弹窗；用户点击后查看当前故障。
   - 故障从有变无：主页故障图标消失。
   - 通知从无变有：铃铛仍在，角标显示当前数量，但不自动弹窗。
   - 通知从有变无：铃铛仍在，角标消失。
2. **故障弹窗已经打开时**
   - 后端增加、删除或替换故障：当前弹窗随聚合轮询直接刷新。
   - 所有故障消失：弹窗不强制关闭，内容切换为“当前无故障”；主页被遮罩区域内的故障图标状态同时由最新快照维护。
   - 用户关闭弹窗只关闭界面，不改变后端故障状态。
3. **通知弹窗已经打开时**
   - 打开弹窗时复制当时最新的通知列表，此后本次弹窗不再接收后端列表变化。
   - 后端随后新增、删除或替换通知，都不改变当前已经打开的弹窗；主页角标仍可按最新运行快照变化。
   - 用户点击某条“确认”：把该通知 `id` 加入本次弹窗的临时确认集合，该条立即隐藏。
   - 当前冻结快照中的通知全部确认后，本次弹窗显示“当前无最新通知”，但不自动关闭。
   - 关闭并重新打开通知弹窗：丢弃上一次冻结快照和临时确认集合，重新复制后端最新通知列表。
   - 重新打开时，后端仍在返回的通知重新显示；后端已经没有通知时显示“当前无最新通知”。
4. **通信中断或本轮读取失败时**
   - 延续总缓存原则：保留最后一次有效故障和通知，不突然清成空列表；同时用数据有效状态表达陈旧。
   - 恢复通信并得到新快照后，再按新列表刷新。

这套策略的目的，是先验证“模拟器变化 → 后端快照 → 主页入口/弹窗实时变化”的闭环。以后如果客户要求真正的通知中心，再单独增加事件编号、发生时刻、已读持久化、历史记录和去重，不反向污染本轮简单模型。

### 8.1 无真实新风设备时的 UI 测试样板

新风、调湿、超净等 4CP 功能的按钮状态必须等待设备实际值读回。未连接模拟器或真实设备时，点击后状态可能不变化，因此不适合作为唯一的 UI 交互测试入口。

空调和地暖当前保持原有本地 UI 逻辑，不接新风模拟器和真实设备也能操作。保留它们的核心价值是提供一组“不依赖设备反馈”的 UI 控制样板，可用于验证：

- 按钮按下和状态反馈；
- 页面进入、返回和切换；
- 档位、温度等调节交互；
- 设置值保存及重新进入后的恢复。

这不是为新风状态做假反馈。新风设备状态仍只认后端周期读取，不能为了方便 UI 测试而由 App 自行伪造；空调和地暖用于承担无设备条件下的 UI 基础交互验证。

### 8.2 485 数值未获取时的显示契约（已确定，待实现）

“未获取显示 `--`”表示后端启动后，该项数据还从未取得过一次有效的设备读回；`--` 只是 UI 占位文本，不是协议值，也不是数值数据字典中的有效值。

后续实现按以下边界执行：

1. 是否取得过有效值由后端判断，App 不根据数值内容自行猜测。
2. 后端内部继续保存类型固定的数值和对应有效标志，不能把 `uint16_t`、温度或浓度字段改成字符串。
3. 聚合 HTTP 快照中，有效数值仍返回 JSON number；从未取得有效值的数值字段统一返回 `null`，不由后端返回字符串 `"--"`。
4. App 将 `null` 显示成 `--`；为兼容旧数据，解析入口可以同时接受历史字符串 `"--"`，但新接口不再生成它。
5. 合法数值 `0` 必须显示为 `0`，不能因为等于零而判成“未获取”。
6. 首次成功读取后，该字段进入有效状态。后续短暂超时、掉线或数据陈旧时，继续保留最后一次有效值，并用 `dataFresh=false` 表达链路状态，不退回 `--`。
7. 不使用系统时间判断该字段是否有效；有效性和新鲜度继续由进程内状态及单调时钟维护。

因此页面显示规则固定为：

```text
后端从未获得有效值       -> HTTP null        -> UI 显示 --
后端获得有效值 0          -> HTTP 0           -> UI 显示 0
后端获得其他有效数值      -> HTTP number      -> UI 显示对应数值
已有有效值后通信暂时失败  -> 保留最后有效值   -> UI 保持数值，dataFresh=false
```

### 8.3 环境数据的显示契约

PRD 确定的是显示范围和样式；Modbus 协议确定的是原始数值。后端先保存协议原值和解码后数值，App 再按显示契约呈现，不反向修改原值。

| 数据 | 协议来源 | PRD 确定显示 | 仍需确认 |
|---|---|---|---|
| PM2.5 | RA1=200FH，OA=2013H，SA=2017H | 整数 0..999；待机页室内/室外数字随等级变色，单位不变色 | 999 以上设备原值的截断/无效处理 |
| 温度 | RA1=200DH，OA=2011H，SA=2015H，有符号原值/10 | UI 范围 -15..45℃，显示整数 | 小数转整数是四舍五入、截断还是只显示设备已为整度的值 |
| 湿度 | RA1=200EH，OA=2012H，SA=2016H | 0..100%，PRD 明确高于 100 时显示 100 | 后端是否同时发布越界标志，避免 App 截断后隐藏传感器异常 |
| CO2 | RA1=2010H，OA=2014H，SA=2018H | PRD 表格给出 0..5000 ppm | 表格中同时存在未完整文字和 999 边界重叠，等修订版确认 |
| 甲醛 | 201AH | 0..2.50 mg/m³，两位小数 | 协议未写单位和缩放比，不能从 uint16_t 直接猜出 mg/m³ |

PM2.5 在 PRD 中有两套颜色语义，必须分开：

| 用途 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| UI PM2.5 数字/动效 | 0..35 绿 #00C853 | 36..75 黄绿 #C6E600 | 76..150 黄橙 #F8B62D | 151..999 紫 #9C27B0 |
| 物理 AQI 指示灯 | 优：绿 | 良：黄绿 | 中度污染：黄 | 重度污染：红 |

因此后端不应使用一个颜色枚举同时驱动 UI 紫色和物理指示灯红色。严重故障的“红色呼吸”又是第三套状态，不从 PM2.5 等级推导。

PRD 还要求根据室内/室外空气质量生成评价提醒，但当前表格只给出了部分“室外中度/重度污染”组合，行列关系不完整。初版只保留评价字段和原始室内/室外等级，不生成一张看似完整但实际靠猜测补齐的文案矩阵。

### 8.4 手动功能与产品策略边界

下列要求已在 PRD 中明确，可作为目标交互，但不能全部等同于单个 Modbus 寄存器：

- 新风：内循环 L1..L5，全热交换 L1..L3，首次开启默认 L2，之后记住最后档位；模式为内循环/全热/自动，首次默认自动，自动时风量不允许手动调整。这部分可与 1006H..1008H、2003H..2004H 对齐。
- 调湿：目标湿度 30..70%，首次默认 60%，之后记住最后值。可与 1003H、100FH 对齐；“单独开调湿时自动开新风”属于后端策略。
- 超净：PRD 要求只能手动开启，时长为 1/2/3 小时/保持，首次默认 2 小时，之后记住最后值。当前协议只有 1002H 超净开关和 1012H IEF 开关，没有明确的超净时长寄存器。
- 空调/地暖：PRD 把它们定义为可选、分区的独立设备，不在本 4CP 寄存器表中。当前 App 的本地 UI 样板继续保留，用于无新风设备时验证按钮、页面、档位和保存交互。

PRD 对超净还存在明显内部矛盾：一处写“与新风、调湿互斥”，另一处把新风系统写成超净的运行前提，并要求根据 CO2 选择内循环/全热。在客户明确前，只保留现有提交的协议等效行为，不新增这段策略。

### 8.5 定时与智能模式

PRD 已确定界面和大部分交互，但定时数据存储、策略执行位置、CO2 阈值和与设备 RTC 的关系都未定稿。

#### 定时

- 新风定时包含开始/结束、单次/工作日/每天/关闭、内循环/全热/自动模式及合法档位。
- 调湿定时包含开始/结束、循环和目标湿度；PRD 要求 CO2 判断高于调湿目标动作，但没有给出 CO2 阈值。
- 多个定时重叠时，最后创建或修改的有效定时优先。
- 任意定时启用时，待机、首页、智能、手动等页面的右上角统一显示定时图标。
- 上述规则不能仅靠 1016H..101FH RTC 字段表达；定时表的数据结构和落盘属于应用/后端策略层，待单独设计。

#### 智能模式

| 模式 | PRD 默认目标 | 目标语义 |
|---|---|---|
| 标准 | 25℃ / 60% | 舒适与能耗均衡 |
| 会客 | 24℃ / 55% | 舒适和空气质量优先 |
| 干爽 | 24℃ / 40% | 以降低室内湿度为主 |
| 温润 | 26℃ / 55% | 以提升/维持湿度为主 |
| 旅行 | 湿度 55% | 低能耗、防霉、最低通风 |

- 任意时刻最多一个智能模式运行；最后有效模式指令优先。
- 智能模式与手动控制不能同时拥有策略控制权；操作手动设备时退出当前智能策略，各模式参数保留。
- PRD 只定义了目标、策略输入和互斥规则，没有给出“综合指标”的完整算法和保护阈值，因此当前可先实现模式数据字典和互斥骨架，不能宣称策略已定稿。

### 8.6 趋势数据

PRD 要求温度、湿度、PM2.5、CO2 提供日/周/月趋势，并给出室内约 5 秒、室外约 10 分钟的数据采样要求。这不是 App 每 2 秒读一次运行快照就能代替的功能：

```text
后端采样/聚合任务
  -> 按数据源采样并保存历史
  -> 生成日/周/月序列快照
  -> HTTP 只读已生成序列
  -> App 绘图
```

当前 DataManager 内存快照只适合最新状态，不能代替长期历史。历史落盘介质、采样时机、断电保留、数据压缩和月视图点数尚未定稿，本轮只记录架构边界，不增加伪历史数据。

## 9. 写入和状态读取的确定语义

```text
App 提交设置
  -> 后端把写任务送入 Modbus 写队列
  -> 调度器在下一拍优先发送写请求
  -> 写响应成功，只代表本次写事务完成
  -> 后续周期读取再次读到对应寄存器
  -> 后端运行快照更新
  -> App 下一次约2秒轮询看到真实状态
```

必须遵守：

1. 写成功和设备实际运行状态是两件事。
2. 不要求写完立刻补读；继续正常周期读取即可。
3. App 不需要知道写插队、250ms 脉搏和寄存器地址。
4. App 的“设置值/意向值”和“设备实际值”分开；设备实际值由后续读取决定。
5. 当前母版的 Modbus 写接口不再提前改实际状态缓存；真实状态只由后续周期读取发布。
6. 写入互斥和可写条件由后端检查；初版 UI 即使允许点击，后端拒绝后实际状态和页面展示也不能变化。
7. 一次操作可能联动多个寄存器；App 下一次聚合读取后统一刷新所有页面和按钮，不只刷新本次点击的按钮。
8. App 不维护 1001H/1002H/1003H 互斥表，也不自行推导 1000H。

## 12. 本轮PRD覆盖与后续实现顺序

本轮已经把PRD的默认值、环境数据显示、首页故障/通知、手动模式、智能模式、定时、趋势和设置维护要求与v1.21寄存器逐项对照。结果分成三类：

1. 可直接映射的协议字段：继续按固定地址填数据字典。
2. PRD目标明确、但不是单个寄存器的能力：进入后端策略、通知或历史任务设计。
3. PRD内部冲突、协议缺少单位/枚举或执行归属不明：列入P02..P25，保留现有等效行为，不抢先实现。

后续三端实现顺序：

1. `1000H` 联动、`1001H/1002H/1003H` 互斥、`1006H..1008H` 条件控制以及故障/通知三端语义已经作为母版落地，后续修改不得倒退为 App 自行推导状态。
2. 下一批完成环境字段逐项有效标志、HTTP `null` 和 App `--` 显示契约，不用 0 伪装未获取。
3. 客户定稿 1007H=1、旁通 UI、IEF 产品含义、CO2 阈值、RTC/时间源和定时存储后，再增加相应业务和策略执行。
4. 趋势历史另建采样/落盘任务；不得让历史处理阻塞 TTY 通信脉搏或 HTTP 快照。
5. 每完成一批，同时校正模拟器镜像、后端数据字典/API和8寸 App 字段，保持一式三份的等效语义。
