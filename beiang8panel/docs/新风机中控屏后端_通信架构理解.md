# 从一台新风机到多路独立通信

## 先从一次真实的新风机动作开始

面板上一次“打开新风”的点击，看起来只是一个 HTTP 请求，实际上要穿过一条有秩序的通信链：后端先校验命令，把它变成新风机写操作；写操作不能和周期采集同时碰串口，必须进入队列；调度器等到上一笔事务结束并满足通信间隔后才发送；写成功之后，还要按相同地址和数量读回设备，确认设备真正接受了改变。

与此同时，周期采集并没有消失。它还在不断读取保持寄存器、输入寄存器和离散输入。某一段读取失败时，后端不能拿半轮新数据覆盖上一轮完整状态；某一次写失败时，也不能因为“命令已经发出”就把界面状态改成成功。于是，新风机后端从一开始就不是一个“收到请求就调用串口”的函数集合，而是一台持续运行的通信状态机：它要安排事务，要维护批次，要决定什么时候把结果提交给外部世界。

第 1 路就是这台状态机的完整产品形态。它一边服务一台新风机，一边还承载面板自己的 WiFi、OTA、雷达、天气和背光能力。所有事情暂时放在一个完整进程里，是因为产品先要把这一条现实链路稳定下来。

当第二台 新风机 设备出现在另一条独立通信口上，真正新增的不是另一套协议。第二台设备仍然说同一种新风机协议，仍然需要同样的读写秩序和确认逻辑；变化的是它有自己的串口、自己的状态、自己的队列、自己的故障和自己的服务入口。问题于是从“怎么再写一套新风机”变成了：“哪些东西应该保持相同，哪些东西必须彻底分开？”

答案构成了后面的架构：新风机的协议语义保留一份；设备差异放进配置；每个设备实例由独立进程承载；通信秩序抽成可以重复装载的调度器。这样，第二路不是复制第一路，而是把第一路中已经分清楚的能力重新装配一次。

第 3、4 路再向下走一步：暂时拿掉 新风机的协议语义，只保留通道和调度骨架，用来确认调度能力本身是否真的独立。于是四路形成的不是四份业务代码，而是一组逐层展开的架构验证。

## 文档结构

全文的核心内容分成两章：第一章讲 新风机 单路内部如何成立，第二章讲这套能力如何走向多路。核心两章之外，再说明实现等级、验证边界和演进方向，最后给出代码落点；这样既保留架构判断，也不把正文写成源码目录。

# 第一章：新风机 内部实现

## 1.1 新风机 Gateway 是协议语义的中心

`BeiAng4CPGateway` 才真正理解 新风机：设备地址、功能码、寄存器区间、帧收发、响应校验，以及寄存器如何转换成业务状态。

它向上承接采集和控制请求，向下使用串口与 libmodbus。它的职责是回答：

```text
这个业务动作对应什么 新风机 操作？
要读哪些寄存器？
要写哪些值？
返回的寄存器怎样解释成业务状态？
```

但 Gateway 不负责决定多个操作之间的执行秩序。它把具体的读写动作交给通信调度器。

## 1.2 调度器不懂 新风机，只管理通信秩序

调度器拿到的是一个可执行操作，而不是某个设备的业务对象：

```text
Gateway 形成读写操作
        ↓
调度器排队
        ↓
唯一工作线程串行执行
        ↓
回调回到 Gateway，发送真正的新风机帧
```

调度器只处理：

```text
读队列和写队列
单线程串行化
写优先级
相邻事务间隔
失败重试
完成回调
```

因此，新风机 Gateway 依赖的是 `CommunicationScheduler` 抽象，而不是某一个固定调度器对象。调度器复用的是执行秩序，Gateway 保留的是协议语义。

> **💡 思想提醒｜操作系统原理思想**
> 可以把这里看成一套很小的通信内核：Gateway 提交操作，调度器决定执行秩序，工作线程是执行上下文；协议内容和调度秩序因此各守其位。

## 1.3 一次通信、一次采集、一次提交不是一个概念

这是内部设计最容易混淆、也最有价值的地方。

一次读取寄存器，是一个通信事务：它遵守响应超时、事务间隔和重试规则。多个读取事务组合起来，才构成一轮采集。只有一轮采集的数据完整，才允许发布新的业务快照。

```text
单次事务：调度器负责执行
采集轮次：DataAcquisitionModule负责组织
状态提交：DataManager负责发布
```

所以 250ms 约束的是相邻通信事务，不是完整采集周期；50ms 是一次设备响应等待上限，也不是下一轮采集时间。

如果一轮采集进行到中间某次读取失败，后面的读取不能继续拼出一份假完整数据。当前轮结束，后续重新开启一轮。上一份完整有效快照继续保留，直到新一轮完整采集成功。

## 1.4 写入是一条“写—确认读—提交状态”链

写入也不是调用一次 `write` 就把状态改掉：

```text
HTTP请求
  → ModbusCommandModule 校验
  → 新风机 Gateway 形成写操作
  → 写队列
  → 调度器执行
  → 写成功
  → 按同一起点、同一数量排确认读
  → 设备读回成功
  → DataManager 整组更新状态
```

这里存在三个不同的成功层次：

```text
HTTP accepted：请求进入执行链
写事务成功：设备接受了写操作
确认读成功：后端确认设备实际状态
```

写失败不启动确认读；确认读失败不发布半组数据。这样，后端不会把“我发过写命令”误当成“设备状态已经改变”。

> **💡 思想提醒｜数据库原理思想**
> 写入后的确认读，决定的不是“有没有发出命令”，而是“哪一份设备状态可以提交”。整组成功才发布，失败就保留上一份有效状态；这让状态变化拥有清晰的提交边界。

## 1.5 新风机 内部的状态边界

新风机 通信线程只负责拿到原始寄存器，解析工作交给独立处理路径；DataManager 负责保存原始镜像、业务字段和通信新鲜度。

```text
通信线程：拿原始数据
处理线程：解析业务语义
DataManager：发布一致快照
HTTP：读取快照或提交命令
```

这形成了一个小型的通信运行时：调度器保证执行秩序，Gateway 保证协议正确，采集模块保证批次边界，DataManager 保证对外状态一致。

# 第二章：新风机 多路扩展

## 2.1 多路扩展的本质：复制实例，不复制实现

多路扩展不是把第 1 路的 新风机 代码拷贝成第 2、3、4 路，而是把同一套抽象重新实例化：

```text
同一套协议实现
同一套调度抽象
        ↓
不同的进程实例
不同的配置实例
不同的调度器实例
不同的通信端点
```

复用的是代码和抽象，私有的是运行状态和通信资源。

> **💡 思想提醒｜操作系统原理思想**
> 多路扩展首先是把每一路变成独立的运行实体：各自拥有资源、线程和状态，各自承担故障；监督进程负责创建、等待和回收它们。这里的关键不是“多启动几个程序”，而是建立多个互不污染的运行边界。

## 2.2 三要素的真正关系

### 配置：定义设备实例

配置把某一路绑定到一个具体通信对象：

```text
FactoryConfig.json   → ttyS2 → HTTP 8080
FactoryConfig_2.json → ttyS3 → HTTP 8081
FactoryConfig_3.json → ttyS4 → HTTP 8082
FactoryConfig_4.json → ttyS7 → HTTP 8083
```

配置描述的是“连接谁、从哪里连接、用什么参数连接”，而不是把调度算法写进去。

### 进程：提供实例边界

每一路由一个进程承载。进程负责这一套 Application、Gateway、调度器线程、队列、状态缓存和串口资源的生命周期。

因此两路使用同一份代码，并不意味着共享同一个调度器或同一个 Gateway 状态：

```text
实现共享
实例私有
资源隔离
故障隔离
```

### 调度器：提供可复用的执行秩序

调度器是被进程装配进去的通信能力。它不等于第几路，也不等于某台设备。

```text
route_id       = 2
scheduler_type = ModbusMasterPolling
```

当前第 2 路直接选择 `ModbusMasterPolling`，表达的就是：第 2 路不是另一种调度器，而是同一种调度能力在另一套进程、配置和通信口上的私有实例。

## 2.3 第 1 路：目前的具体完整实现

第 1 路是当前产品业务的基准实现：

```text
Full
  → DataManager
  → DataAcquisitionModule
  → ModbusCommandModule
  → BeiAng4CPGateway
  → ModbusMasterPolling
  → ttyS2
```

它除了 新风机 通信，还承载 WiFi、OTA、雷达、天气、背光等本机能力。因此第 1 路是目前需要保持兼容的具体业务实现，不是单纯的测试槽位。

## 2.4 第 2 路：验证 新风机 抽象和调度器复用

第 2 路保留 新风机 通信主干，但去掉第 1 路的本机能力：

```text
FourCpCommunication
  → DataManager
  → DataAcquisitionModule
  → ModbusCommandModule
  → BeiAng4CPGateway
  → ModbusMasterPolling
  → ttyS3
```

它验证的是一个受控变化：

```text
新风机协议不变
Gateway不变
调度能力不变
进程变了
配置变了
通信口变了
```

如果第 2 路能独立运行，就说明 新风机 Gateway 没有绑死第 1 路的进程、串口或调度器状态；同一个通信调度器抽象可以服务第二个独立的 新风机 设备实例。

这不是复制第二份 新风机，而是：

```text
一个新风机通信实现
两个Gateway实例
两个调度器实例
两个设备上下文
```

## 2.5 第 3 路：通用通信与调度策略测试

第 3 路不承担完整新风机业务，而是走通用通信路径：

```text
CommunicationOnly
  → CommunicationChannel
  → CommunicationScheduler
  → SerialCommunication
```

这样测试对象就从“新风机协议是否正确”转成了通信骨架本身：

```text
调度器能否脱离新风机独立运行
通道能否独立持有调度器
不同策略能否并列存在
不同端点能否独立运行
增加通信实例会不会污染已有实例
```

第 3 路当前改变调度策略，用来观察通用 Channel 在不同调度规则下的行为。它是可改动的测试位，不是第 1 路业务的复制品。

## 2.6 第 4 路：并列的独立扩展实例

第 4 路与第 3 路并列，不是第 3 路的附属配置。它拥有自己的配置、通信端点、进程、Channel、调度器实例和 HTTP 端口：

```text
FactoryConfig_4.json
    → /dev/ttyS7
    → CommunicationOnly
    → CommunicationScheduler4
    → HTTP 8083
```

它验证的是再增加一路之后，原有进程和调度器实例是否仍然保持独立。第 3 路可以改变策略，第 4 路可以替换为另一种策略或新的通信实现；两者都是可调整的测试与扩展位置，彼此没有从属关系。

## 2.7 当前四路的成熟度不是相同的

```text
第1路：当前完整、真实的产品实现
第2路：新风机复用和独立实例验证
第3路：通用调度与通信通道测试
第4路：多路扩展和后续试验预留
```

所以不能要求第 2、3、4 路永远复制第 1 路的全部模块；它们的意义恰恰是允许调整组合，验证边界，然后为以后接入更多设备、协议或通信介质提供位置。

## 2.8 最终模型

```text
                       通信调度器抽象
                              │
           ┌──────────────────┼──────────────────┬──────────────────┐
           │                  │                  │                  │
       调度器实例1         调度器实例2         调度器实例3         调度器实例4
           │                  │                  │                  │
        新风机Gateway1     新风机Gateway2      通用Channel3       通用Channel4
           │                  │                  │                  │
        Config1/ttyS2      Config2/ttyS3      Config3/ttyS4      Config4/ttyS7
           │                  │                  │                  │
        Process1           Process2           Process3           Process4
```

这张图中，向下是具体化，横向是实例化：

```text
向下：抽象逐层落到协议、通道和设备
横向：同一抽象被复制到不同进程和配置
```

这就是当前架构的真正价值：**不把 新风机 写成一套只能服务一台设备的专用程序，而是把它变成可以被多个独立运行实例装载的通信能力。**

# 第三章：实现等级、验证边界与后续演进

## 3.1 当前实现和测试位不是同一等级

第 1 路是当前完整的产品实现，承担真实的 新风机 业务和本机能力，是需要保持兼容的基准。第 2 路是第二个 新风机 通信实例，用来验证同一套协议 Gateway 和通信调度抽象，能否在另一进程、另一份配置、另一独立通信口中再次成立。第 3、4 路则是通用通信测试和扩展位置，可以调整调度策略、通信通道和角色，不应被误读为第 1 路的复制品。

因此，四路的通过并不是同一种验收：第 1 路证明当前产品链路，第 2 路证明 新风机 通信抽象的多实例复用，第 3、4 路证明调度器和通用通道可以脱离完整 新风机 业务继续扩展。

## 3.2 后续可以沿组合关系扩展

增加第二个同类设备时，主要增加配置和进程实例，不复制 新风机 Gateway；增加新的调度策略时，只替换调度策略，不改协议语义；增加新的通信介质或协议时，增加对应 Channel 或 Gateway，不把新介质写入进程监督器；增加本机能力时，放进完整业务进程或独立 daemon，不反向污染通信调度器。

扩展的前提是继续守住三个边界：每一路独占自己的通信资源；调度器只处理操作秩序；协议和设备差异留在 Gateway/Channel。边界一旦被打破，多路就会退化成多个互相复制、互相牵连的专用程序。

## 3.3 当前代码与文档的语义

当前工作树中第 2 路已经选择 `ModbusMasterPolling`，表达的是与第 1 路使用同一种调度能力、但创建独立实例。部分旧文档仍把 `CommunicationSchedulerType_2` 写成第 2 路实际调度器，容易把“实例编号”和“调度策略”混在一起；后续应统一这一层语义。

# 附录：代码阅读落点

```text
main.cpp
  进程定义、配置槽位、进程角色和调度器选择

ProcessSupervisor.cpp
  fork、等待、退出和信号转发

common/Application.cpp
  按角色装配完整业务、新风机通信或通用通信

DataManager.cpp
  读取配置、创建调度器并注入新风机 Gateway

gateways/BeiAng4CPGateway.cpp
  新风机协议读写、确认读和设备状态回调

gateways/ModbusMasterScheduler.h/.cpp
  调度器抽象的公共执行机制和策略实例

gateways/CommunicationChannel.cpp
  通用通信进程使用的传输通道和调度器持有关系
```
