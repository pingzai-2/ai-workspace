# 后端实现框架

## 1. 文档定位

本文说明当前后端母版的进程、调度、缓存和对外服务边界。协议地址、位定义和产品业务字段不在本文重复维护，分别以协议文档和产品清单为准。

框架目标不是把某一份协议写死在通信代码中，而是稳定以下机制：

1. 一路通信通道只由一个进程独占。
2. 进程与通信调度器明确组合，后续可以并列增加进程或新增调度器。
3. 通信传输、协议解析、本机能力、网络服务和 HTTP 返回互不阻塞。
4. HTTP 只读内存快照或提交命令，不直接访问通信通道、sysfs 或外部网络。
5. 写入成功不伪造实际状态；实际状态由设备读回值驱动。

## 2. 总体结构

```text
进程配置区
  ├─ 进程 1：配置 1 + 通信通道 1 + ModbusMasterPolling（兼容入口）
  ├─ 进程 2：FactoryConfig_2 + 通信通道 2 + CommunicationSchedulerType_2
  ├─ 进程 3：FactoryConfig_3 + 通信通道 3 + CommunicationSchedulerType_3
  └─ 进程 4：FactoryConfig_4 + 通信通道 4 + CommunicationSchedulerType_4

完整业务进程（进程 1）
  ├─ DataManager                 状态中心和统一快照
  ├─ DataAcquisitionModule       通信通道周期采集与协议解析
  ├─ ModbusCommandModule         控制策略、写队列和写后确认读
  ├─ LocalDeviceModule           板端本机能力
  ├─ WifiManager                 WiFi命令队列(扫描/连接/断开/开关/对时)
  ├─ OtaManager                  模组串口常驻持有+OTA+0x11重连通知钩子
  ├─ ScheduleController          定时任务
  ├─ Application::setRs485Enabled RS485全停开关(定时任务丢弃+命令队列+轮询, UDISK持久化)
  └─ HttpServer                  统一读取和命令入口

4CP 通信进程（进程 2）
  ├─ DataManager                 本进程通信状态中心
  ├─ DataAcquisitionModule       本进程通信通道周期采集与协议解析
  ├─ ModbusCommandModule         本进程控制写入和写后确认读
  └─ HttpServer                  只注册协议、状态和通信接口

通用通信进程（进程 3/4）
  ├─ CommunicationChannel        持有本进程唯一传输通道
  ├─ CommunicationScheduler      只负责操作排队和执行策略
  └─ HttpServer                  只注册通用通信状态和原始操作接口

通信进程不创建 `LocalDeviceModule`、`WifiManager`、`OtaManager`、屏幕/雷达/天气等本机
能力模块。每个进程仍然独立创建自己的 `Application`、`DataManager`、队列和 HTTP 服务；
4CP 进程额外持有 Gateway，通用通信进程只持有 `CommunicationChannel`。
```

进程 1 当前把“设备通信”和“本机设备信息/本机能力”放在同一个完整
`Application` 技术栈中，这是既有 4CP 兼容结构，不是新增通信进程的模板。逻辑上两者应当
拆开：通信进程只负责自己的通道、调度器和通信接口；WiFi、OTA、背光、雷达、天气等本机
能力只属于完整业务进程。后续新增通道或协议时，不复制进程 1 的本机能力，也不反向改动
进程 1 的兼容入口。

### 本机能力与通信调度器边界

通信调度器默认服务对外设备通信：为一路独立通道提供操作排队、执行策略和底层串行化。
本机设备能力默认由自己的工作线程、系统接口或独立 daemon 处理，不因为存在“通信”二字就
强行接入通信调度器。只有当某个本机模块本身出现复杂的读写队列、重试、优先级或并发仲裁
需求时，才在该模块内部局部复用调度器；复用不改变本机模块与其它通信进程的独立边界。

当前 TRMK222 雷达属于本机能力：雷达 daemon 独占实际串口，后端通过状态文件读取、命令文件
下发开关，不经过 `CommunicationScheduler`。这种文件桥接方式继续保持，不占用进程 1/2/3/4
的通信通道。

当前 `main.cpp` 中每个配置文件形成一个 `BackendProcessDefinition`，并明确选择一个 `CommunicationSchedulerType`。`ProcessSupervisor` 只负责创建、等待、回收和转发信号，不承担协议逻辑。

当前已经落地的调度器类型为：

| 类型 | 当前行为 |
|---|---|
| `ModbusMasterPolling` | 进程 1 既有 4CP 调度器入口 |
| `CommunicationSchedulerType_2` | 独立队列策略，进程 2 使用 |
| `CommunicationSchedulerType_3` | 读队列优先，进程 3 使用 |
| `CommunicationSchedulerType_4` | 写队列优先，进程 4 使用 |

这些类型只决定同一路通信队列的选择策略，真实读写操作由通道和设备实现执行。进程 1
继续使用现有 4CP/Modbus Gateway；新增 CAN、网口或其它协议时，只需新增对应通道和设备
实现，不把具体介质名称写入通用调度器或进程监督框架；
`ProcessSupervisor`、进程生命周期和 HTTP 边界不需要改成多路耦合。

默认配置文件：

| 文件 | HTTP 端口 | 当前通道端点示例 | 进程角色 |
|---|---:|---|---|
| `FactoryConfig.json` | 8080 | `/dev/ttyS2` | 完整业务进程 |
| `FactoryConfig_2.json` | 8081 | `/dev/ttyS3`（当前配置值，节点存在） | 4CP 通信进程 |
| `FactoryConfig_3.json` | 8082 | `/dev/ttyS4`（当前配置值，节点存在） | 通用通信进程 |
| `FactoryConfig_4.json` | 8083 | `/dev/ttyS7`（R818 `evb2` 实机节点） | 通用通信进程 |

R818 `r818-evb2` 系统当前提供的通信 UART 节点是 `ttyS2`、`ttyS3`、`ttyS4`、`ttyS7`；
进程 1 现有 4CP 配置使用 `/dev/ttyS2`；当前附加三路使用 `S3/S4/S7`。这里的逻辑通道
编号（1/2/3/4）不等同于 Linux UART 编号，最终绑定必须同时满足目标板设备树、实机节点
和物理线序。
各进程不得共用同一个通信通道或 HTTP 端口。

附加配置的 `transport.endpoint` 设为 `null` 时，表示停用该配置对应的通信进程；代码和
配置文件仍保留，后续只需恢复实际端点即可重新启用。停用时保留配置槽位，不能让后面的
逻辑通道顺延占用前一个进程角色。

### 配置读取和失败边界

每个进程启动时读取自己的 JSON 一次：先检查文件可读、JSON 语法、根对象、通信段、网络
段以及已出现字段的类型和范围；全部通过后才一次性提交运行态配置。解析中途或任何校验失败
都不会留下半套成员值，也不会套用默认串口、默认 HTTP 端口继续运行。

启动前还会检查各路 endpoint 和 HTTP 端口是否重复；串口打开时做轻量独占声明。文件缺失、
损坏、字段异常、端点不存在或被占用，只停止对应进程，不影响其它独立进程。运行中端点出现
`EIO`、`ENODEV` 等硬件级错误时停止该通信路；仅设备协议超时仍按现有重试、退避和 stale
机制处理。

配置不运行时热加载。退出时不自动保存；未来只有受控运行时接口实际改变配置并确认成功后，
才显式使用临时文件、原子替换和读回校验保存，保存失败保留原文件。

## 3. 一路通信通道的调度

### 3.1 单一所有者

同一路通信通道的所有底层操作都进入同一个调度器工作线程。进程 1 的
`ModbusMasterScheduler` 仍负责现有 4CP 调用；通用进程使用同一套队列实现但不绑定协议：

```text
读操作 ─┐
写操作 ─┼─> 读队列 / 写队列 -> 唯一调度线程 -> 通信通道
控制操作 ─┘
```

外部线程不得绕过调度器直接操作同一个 libmodbus 上下文。这样可以保证一条串口上任何时刻只有一个完整事务。

### 3.2 通信脉搏

进程 1 的现有 4CP 实现参数：

| 项目 | 当前值 | 语义 |
|---|---:|---|
| 相邻事务间隔 | `250ms` | 上一事务结束后至少等待 250ms 再开始下一事务 |
| 单次响应超时 | `50ms` | 一次 libmodbus 事务等待设备响应的上限 |
| 最大尝试次数 | `2` | 首次尝试失败后再重试一次 |
| 单次寄存器读取上限 | `50` | 大数据区拆成多个连续区间读取 |

一次调度只执行一个事务。事务执行期间不能被打断；结束后重新检查队列。写队列始终优先于读队列，因此周期读 1、2、3……之间如果出现写入，当前读完成后先处理全部已排队写任务，再继续后续读任务。

失败重试也重新进入调度选择。两次尝试之间若有其他写入排队，下一拍仍按写优先重新选择，不在一个函数内部连续睡眠重试。

### 3.3 异常恢复

每次底层事务前清理无效残留，超时、CRC 错误或无效帧后重新同步 RTU 输入。连接失败与设备无响应分开处理：串口节点消失时使用退避；串口仍在但设备无响应时保持较快探测。

串口打开成功只表示文件描述符可用，不等于设备在线。重连后的真实读事务成功，才证明通信恢复。

## 4. 采集与处理分离

`DataAcquisitionModule` 分为两条路径：

```text
通信线程
  -> 按有效区间分段读取原始寄存器/位
  -> 形成完整 RawRegisterCache
  -> 投递给处理队列

处理线程
  -> 从原始镜像解析协议字段
  -> 生成 GatewayData / EnvironmentData
  -> 在一把数据锁内发布语义数据和原始镜像
```

通信线程只负责尽快获取数据，不做慢业务处理。处理线程可以逐步扩展字段解析，但不能反向占用 TTY。

只有保持寄存器、输入寄存器和离散输入三部分均完整有效时，才发布一轮完整周期快照。不完整采集不得用半组新值覆盖上一份有效业务数据。

## 5. 写入与确认读

HTTP 控制接口的成功响应表示命令已通过校验并成功进入调度队列，不表示设备已经执行。

```text
HTTP 控制请求
  -> ModbusCommandModule 校验范围、条件和互斥关系
  -> 形成一个或连续 N 个寄存器的完整写入意向
  -> 写任务进入写队列，HTTP 返回 accepted
  -> 调度器完成写事务
       ├─ 失败：结束，不改变实际状态缓存
       └─ 成功：把同一起始地址、同一 N 个寄存器加入确认读队列
  -> 确认读成功
  -> 同一把数据锁内整组替换原始值并重新解析相关业务字段
  -> HTTP 运行快照后续返回实际读回状态
```

必须满足：

- 写失败不启动确认读。
- 确认读失败、数量不符或越界时不发布半组数据。
- 写入和确认读仍经过同一通信调度器，不建立第二条串口通道。
- 写了连续 N 个寄存器，就精确回读相同起点和数量。
- 正常周期读继续运行，最终会再次校准完整状态。

模块开关按 v1.22 直接单写对应寄存器：新风写 `1001H`、超净写 `1002H`、调湿写 `1003H`；互斥联动由 4CP 设备执行，后端不维护第二份互斥意向表，也不替设备改写读回值。快捷关机是例外，使用一次 10H 将 `1001H..1003H` 全部写为 0。

写成功后按相同起点和数量排队确认读。这里的“原子事务更新”只描述确认读发布：原始寄存器镜像和业务字段在同一把数据锁内一起更新，HTTP 不会看到半组新值、半组旧值；它不表示后端把三个模块开关合并成一帧控制写。

## 6. 数据中心与 HTTP 快照

当前统一读取结构为：

```cpp
struct BackendRuntimeSnapshot {
    GatewayGeneralDataStructure gatewayData;
    EnvironmentDataStructure environmentData;
    LocalDeviceDataStructure localDeviceData;
    ModbusRegisterCache registerCache;
    bool dataFresh;
};
```

HTTP 读取流程：

```text
HTTP 请求
  -> DataManager 加短锁
  -> 一次复制协议业务数据、环境数据、本机数据、原始寄存器和 dataFresh
  -> 立即解锁
  -> 锁外组装 JSON 并返回
```

等待同一把数据锁是允许的，因为锁内只做定长内存复制，不访问串口、文件、sysfs、外网，也不做 JSON 序列化。数据量扩大时，应先减少锁内工作，而不是立即拆出多套互相不一致的缓存。

## 7. 30 秒通信新鲜度

`dataFresh` 使用进程内 `steady_clock`，不依赖板端可能错误的系统时间。

计时规则固定为：

```text
任意一次真实 Modbus 读事务或写事务成功
  -> 记录单调时钟时刻
  -> 未满 30 秒：dataFresh=true
  -> 达到 30 秒：dataFresh=false
  -> 下一次真实事务成功：立即重新计时并恢复 true
```

以下事件不能刷新计时：

- 串口仅打开或重连成功；
- HTTP 命令仅成功入队；
- 解析线程仅重新发布旧缓存；
- HTTP 仅返回上一份快照。

数据陈旧后继续保留最后一次有效值，不清零、不使用用户意向覆盖。前端据此显示“设备数据陈旧”；HTTP 本身不可达则由前端独立判定为“后端服务离线”。

## 8. 非 TTY 能力

非 TTY 能力与串口调度器分离：

```text
本机设备线程（LocalDeviceModule）
  -> 本机数值调节、传感器、状态文件、指示灯等能力
  -> 发布 LocalDeviceData 缓存

系统网络线程（WifiManager）
  -> Wi-Fi 开关、扫描、连接、断开和状态查询
  -> 发布 LocalDeviceData.wifi 过程快照

外部网络服务
  -> 天气、IP 等外部网络能力
  -> 发布 NetworkData 缓存（目标结构）
```

当前本机硬件和 Wi-Fi 已分别有独立工作线程与缓存，两者都不进入 TTY 调度器。天气/IP 在逻辑上独立于 TTY，但仍有部分同步 HTTP/TTL 处理；后续应收口为独立网络工作线程，业务 HTTP 只读网络缓存。

过程型操作采用“命令入队 + 状态缓存”。HTTP POST 只返回 `accepted`，独立工作线程再发布 `scanning / connecting / connected / disconnecting / failed`。前端通过统一运行快照读实际结果；页面返回、重建或关闭都不得取消后端过程。

复杂过程型能力采用“单一发布者、整组快照”的轻量事务边界。HTTP 线程只把命令放入队列，不提前修改过程状态；同一个工作线程依次发布本条命令的 `pending`、执行结果和周期查询结果。每次发布都先形成一份完整状态组，再由状态中心在现有数据锁内整组替换，不能让上一条命令的完成结果覆盖下一条尚未执行命令的 `pending`。这里的原子性只保证一次内存快照内部自洽，不把 HTTP 请求、平台命令和后续轮询锁成一个强事务；前端短暂读到上一份完整快照是允许的，下一次正常轮询按最新结果纠正，不为此增加等待、重试或额外轮询。

Wi-Fi 系统适配器只执行固定程序和参数，不经 shell 拼接命令。后端不保存、不记录密码；密码仅存在本次连接命令生命周期中。是否记住凭据由前端在聚合快照确认同一 SSID 已连接后决定。

Wi-Fi 关闭是一条明确的断开命令，不是只改缓存布尔值。`enabled=false` 入队后，工作线程执行平台适配器的断开操作；执行成功才原子更新为 `enabled=false, connected=false`并清除 SSID/IP，执行失败保留上一次确认缓存并发布错误。“App 启动时按保存开关同步一次”属于前端策略；后端只需保证每个被接受的关闭命令都真实执行一次，不自行循环重发。

普通 `disconnect` 与关闭开关不是同一语义。普通断开仍调用平台断开操作，但成功后保持
`available/enabled`，只清除当前连接的 SSID、IP 和 RSSI，扫描列表与前端保存的凭据不受影响。
后端不负责自动重连和凭据 LRU；App 是否在启动、后端恢复或重新开启时尝试一轮连接属于前端策略。
平台网络守护进程若自行恢复历史连接，后端状态查询按实际结果发布，不把来源猜测成 App 命令。

扫描由同一 Wi-Fi 工作线程顺序执行，连接、断开和开关命令与扫描不会并行访问平台工具。扫描成功
原子替换扫描快照，失败保留上一份有效列表；扫描触发周期由前端页面策略决定，后端不自设页面定时器。

单个连接事务采用 20 秒总期限：平台连接命令和状态确认共享同一个单调时钟截止点，不能分别累计
20 秒。每个连接命令带有递增序号；新的连接、断开或关闭命令到来时，工作线程使旧连接序号失效，
正在运行的旧平台工具在下一次轻量轮询中终止，旧事务不得再发布失败或成功覆盖新事务。候选扫描同样
允许被连接类命令抢占，因此用户连接不必等待最长 15 秒的扫描结束。

后端只提供“当前连接事务可抢占”能力，不保存 LRU 队列，也不判断命令来自自动还是手动。前端若在
自动连接某项期间提交手动连接，后端立即以新命令替换旧命令；手动失败后是否重新提交刚才被打断的
自动项，由前端策略决定。页面返回不会产生取消命令，只有新的明确连接目标、普通断开或关闭开关才
会终止当前连接事务。

### 8.1 本机接口轻量读写契约

本机能力的读取和写入都按各自接口契约处理，不识别操作系统、板型或产品身份，也不增加通用的过度防护。这样同一后端运行在 macOS、普通 Linux 或未接外设的测试环境时，只会得到“接口不可用”，不会猜测路径、修改权限或操作未知节点。

读取流程：

```text
固定读取接口
  -> 检查路径存在且当前可读
  -> 按该接口已确认的格式读取、解析
  -> 成功：只更新本次取得的字段
  -> 失败：保留上一次缓存基准，不写 0、不清空、不强制改成 --
```

缓存基准可以来自上一次成功读取、持久化数据、离线 JSON 模板、普通默认值或 `--`。采集模块只负责“成功才覆盖”，不规定初始基准必须是哪一种。部分字段读取成功时只更新成功字段，不能因同组其他字段失败而整组清零。

写入流程：

```text
固定写入接口
  -> 检查路径存在且当前可写
  -> 按该接口契约执行写入
  -> 接口有返回值时按返回值判断；void/无结果接口在调用完成且无可检测异常时按成功处理
  -> 有安全、明确的回读接口时再读取实际生效值
  -> 发布命令 success/error 和确认后的缓存值
```

写入结果分三类：

1. 写入失败且没有有效返回值：保留上一次确认值，前端可回退原样。
2. 写入成功但接口不返回实际值：采用用户请求值。接口本身为 `void` 或没有成功状态时，只要调用已经完成且未发生可检测异常，也按写入成功处理。
3. 接口返回实际生效值：以实际值为准。例如请求 `100`、设备返回 `95`，缓存发布 `95`。

安全边界：

- 不做平台或板型识别，不因运行在非目标平台而执行额外探测。
- 不强制写前读取；没有明确、安全回读能力的接口不主动读取。
- 不用通用逻辑推断数值范围、单位或设备能力，只使用该接口已经确认的契约。
- 不创建未知节点，不执行 `chmod`、`sudo`，不主动修改权限。
- 不执行物理“回滚写入”；失败只保留后端缓存和界面的上一次确认值。
- 已有白名单机制时使用白名单；没有时由每个适配器固定自己的路径或命令，不额外搭建复杂识别系统。

### 8.2 本机读写的通用模型

本机能力按接口契约归入以下通用模型，而不是为每种设备单独发明流程：

1. **只读采集器**：温湿度、序列号、状态文件等。成功才覆盖对应缓存，失败保留当前基准。
2. **只写执行器**：没有实际值回读的接口。存在明确写结果时按结果判断；`void`/无结果接口调用完成且无可检测异常时按成功处理。成功采用请求状态，失败保留旧确认值。
3. **本地数值调整器（通用特例）**：同时具备明确读、写接口，设备还可能对目标值限幅。写后必须从同一个接口回读并发布实际值。
4. **过程型操作**：Wi-Fi 扫描、连接等。命令入队后由状态缓存持续发布处理中、成功或失败，不让 HTTP 阻塞等待全过程。

#### 本地数值调整器

本地数值调整器是可复用机制，不绑定具体设备或平台。某项能力只有同时确认安全读写接口后，才可采用该模型。它不采用“写成功但无返回值就直接采用请求值”的只写执行器分支：

```text
写入目标值
  -> 从刚刚写入的同一个接口立即回读
  -> 回读成功：发布设备实际值
  -> 回读失败：保留旧确认值，发布确认失败
  -> 后续周期读取成功：再发布新的实际值
```

该特例仍不做写前预读，不执行物理回滚。回读只针对已经确认安全、且与本次写入同源的固定接口，避免多个同类节点之间串读。

## 9. 扩展规则

新增协议或设备时按以下顺序：

1. 在协议数据结构中保留完整原始区，未处理字段也有稳定位置。
2. 调度器只负责通信次序，不识别产品业务。
3. 采集线程只获取数据，处理线程再按地址、偏移和位定义填充业务字段。
4. HTTP 只读取快照或提交命令，不直接操作设备。
5. 新角色通过新调度器接入，新通信通道通过新进程接入。
6. 只有协议或硬件来源已确定的字段才进入业务层；待确认字段保留原始值。

## 10. 当前验证边界

母版自动测试已覆盖：

- 写优先、一拍一任务、一次重试重新入队；
- 原始快照解析和写后连续区间发布；
- 模块互斥、写入条件和快速连续意向；
- 30 秒新鲜度边界：`29999ms` 新鲜、`30000ms` 陈旧、成功通信后恢复。

主机编译和自动测试通过只能证明源码级行为。真实串口抗干扰、板端资源、驱动节点和进程启动顺序仍需在目标设备上验收。
